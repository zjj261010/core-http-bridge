# 管理平台二次改造方案：镜像、服务与启动模式

版本：用户确认补充版 v2.2，附 v2.3 实施状态。基线：`cf42836`。状态：**主要流程已实施，具体覆盖与限制见《二次改造实施与验收记录》**。

本版依据用户最新要求重写，替代此前“靶标资源优先、详情独立页、通用版本发布工作流”的提议。此前外部风格参考继续沿用，但信息架构、服务模型和交互以本版为准。v2.2 为设计阶段；用户随后明确要求“开始执行”，已实施业务页面与后台主流程，完成隔离环境真实验收。没有主动重启 CORE。

## 1. 已明确的产品要求

| 用户要求 | 本版落点 |
| --- | --- |
| “导入标靶包”改成“导入”，镜像不一定是标靶 | 全部镜像入口使用通用名称，不要求先建立靶标实体 |
| 点击镜像详情弹出弹窗 | 一级弹窗上方为镜像基本信息，下方为可增删改的服务表格 |
| 点击服务详情，再弹出表格 | 二级弹窗管理该服务的不同启动模式及各自脚本 |
| 模式可以导入启动脚本 | 按模式导入、替换、导出脚本，界面无需填写服务类或配置代码 |
| 注册需要在最后点击确定，并增加重启提醒 | 子弹窗修改先暂存；一级弹窗最后统一检查变更、提示 CORE 重启影响，再明确提交 |
| 去掉镜像弹窗中的独立容器验证 | 本工作流不提供验证容器、试运行或自动创建容器入口 |
| 镜像声明全量服务，供后续选择 | 服务清单表示镜像提供的能力；模板提供默认启用服务和模式，拓扑节点可单独覆盖 |
| 区分镜像服务与 CORE 原生服务，保留自动前缀思路 | 内部自动命名空间 + 明确来源字段 + 按运行时过滤；显示名不带内部前缀 |
| 去掉版本草稿与发布、拓扑草稿与部署入口 | 导航不再提供这两个模块；内部一致性和历史修订继续保留 |
| 拓扑全部放入拓扑管理 | 列表、画布、导入导出、启动停止和执行记录归入同一模块 |
| 所有页面不填改 JSON | 统一使用表格、表单、文件导入导出；不保留高级 JSON 编辑/查看入口 |

设计阶段的“继续”用于细化交互原型；后续“开始执行”已进入实际实施。原型检查与正式功能验收分开记录，不以原型通过代替产品测试。

### 1.1 本轮确认纳入的六项补充

1. 删除服务只移除声明，不卸载镜像中的软件；暂时不运行应在模板或节点取消启用。
2. 模板提供默认服务配置，拓扑节点可以单独覆盖并恢复默认；部署时冻结实际配置。
3. 只对同一节点实际启用的服务组合检查端口、依赖和启动顺序，不把完整服务清单当作同时启动清单。
4. 编辑时及时校验，最后确定才注册；保存或注册失败保留编辑内容与明确的处理阶段。
5. 最多两层业务弹窗，返回原服务行并标记变更；各层取消只撤销各自的修改。
6. 导入先按新增、替换、跳过预览冲突；导出明确区分配置与脚本、完整镜像包。

## 2. 导航与管理对象

```
资源管理
  镜像管理          ← 默认入口
  容器管理          ← 原有独立容器能力，可单独访问
  节点模板
仿真管理
  拓扑管理          ← 拓扑列表 / 画布 / 运行记录
运行记录
  数据监测
  审计日志
```

导入任务在镜像管理内可查询，并可作为全局任务入口的过滤视图。它不是新增的版本构建模块。

镜像可以是基础环境、工具环境、普通应用环境或演练环境。列表不再把所有镜像都叫靶标，不为工具镜像强制生成 normal/vuln 两种服务。

## 3. 镜像列表与导入

### 3.1 镜像列表

建议列：镜像名称/标签、大小、平台、声明服务数、配置生效状态、更新时间和操作。主操作为“详情”；导入按钮统一为“导入”。

同一 image ID 的标签可以聚合展示，但每个别名仍可明确选择；使用完整 image ID 固定内容，tag 不作为不可变内容身份。构建时间、首次发现时间和实际导入时间分别记录，未知导入时间显示“未记录”。

状态使用用户可行动的描述：未配置服务、配置已生效、有未提交修改、已保存待生效、注册失败、镜像缺失。无后台服务的工具镜像可以保留空清单，不显示“必须补服务”。

### 3.2 导入

保留本机上传、服务器路径，以及镜像/服务/说明文件整体或分件导入能力。导入页只选择文件、目录和来源，不粘贴 JSON、Python 服务定义或 shell 源码。

识别结果展示为镜像表、服务表、模式表和文件列表，冲突由用户通过表格选择处理。镜像文件接收/载入是独立后台步骤，不因取消后续服务编辑而删除已经成功载入的镜像。

导入的服务和模式先进入待确认配置，不在解析文件或选择脚本时直接写入 CORE 注册池。导入完成后自动打开对应镜像详情，用户继续核对服务并在最后确定。

上传中断与后台导入中断分别处理。首期沿用现有上传能力，不承诺尚未实现的浏览器断点续传；接收完成的文件和后台任务结果可继续复用。

### 3.3 导入冲突与导出范围

导入预览按“镜像 → 服务 → 模式 → 文件”显示匹配对象、当前内容、导入内容和处理结果。优先按稳定标识匹配；只有名字相同但没有稳定标识时须确认归属，不能直接覆盖。每行允许新增、替换、跳过，提供批量选择但不默认覆盖全部。

替换服务时必须明确是否替换该服务完整声明及全部模式；替换模式须显示脚本、依赖、端口等差异。新增对象生成新标识，改显示名称不改变身份。无法映射的依赖、缺失脚本和重名对象在预览中指出；确认后合入父弹窗工作副本，仍不注册。跳过项不改变现有配置。旧修订引用的文件继续保留。

导出菜单提供两种主要范围：

| 范围 | 内容与用途 |
| --- | --- |
| 配置与脚本 | 镜像内容标识、服务/模式清单、参数、依赖与脚本附件；用于修改配置、复用服务，无需传输镜像本体 |
| 完整镜像包 | 配置与脚本，加实际镜像本体；用于交付或迁移到没有该镜像的环境 |

导出前列出包含项、附件缺失项和可确定的体积；完整包走后台任务，显示进度及结果。镜像本体不存在时不能提示完整包导出成功。只导出配置不意味着脚本遗漏，配置与脚本默认共同打包；如需单个脚本，可在模式表中导出。

## 4. 一级弹窗：镜像详情

### 4.1 基本信息区（上方）

按字段展示名称与标签、完整 ID、平台、大小、工作目录、启动入口、创建/导入时间和备注。必要的环境变量、端口、挂载等展开成键值/行表格，不直接展示 inspect JSON。

“镜像说明”“备注”等使用普通文本输入，端口使用协议/端口/说明行，环境变量使用名称/值行。未知扩展字段保留并按字段结构递归展示；尚不支持编辑的部分只读并可原样导出，不用原始 JSON 填补界面缺口。

### 4.2 服务表格（下方）

**一行对应一个逻辑服务，不对应一个启动模式。**

建议列：服务名称、软件版本、用途/端口、模式数、配置状态和操作。

- 新增服务：追加一行或打开弹窗内的小表单，填写服务名、软件版本、说明和端口。
- 编辑服务：行内编辑并保存到当前弹窗的暂存区。
- 删除服务：在当前弹窗内确认该行及其模式将从声明中移除，展示现有模板/部署引用影响；不再叠第三层弹窗。
- 服务详情：打开该服务的二级模式弹窗。
- 导入/导出服务清单：读取/生成文件，界面仍以表格查看和处理。

清单应包含镜像中所有需要被选用/管理的服务，如 HTTP、SSH、Redis、定时服务等，不仅是演练服务。不扩张为自动扫描所有安装包；工具软件不必被伪装为后台守护服务。

删除声明不会卸载镜像内的软件，也不表示已有节点上的进程已经停止。删除用于纠正错误或过期的声明；如果只是这次不运行，应保留全量清单，在模板或拓扑节点取消启用。受引用声明移除只影响新配置的选择范围，历史实现继续保留；旧配置升级时逐项处理引用，不能静默删掉节点的已选服务。

### 4.3 暂存与取消

一级弹窗打开时获得配置基准和修订号，编辑使用独立工作副本。

- 行保存只更新工作副本。
- 二级弹窗“确定”只合并回一级工作副本。
- 一级弹窗“取消”放弃本次服务配置修改；关闭有修改时提醒。
- 一级弹窗“确定”才进入变更汇总和注册提醒。

用户关闭二级弹窗不应丢失一级已编辑的其他服务；子弹窗取消只撤销该服务本轮模式编辑。导入文件的接收与清理按文件所有权单独处理，不能误删已被后台任务引用的文件。

返回父弹窗时恢复原列表位置，并将键盘焦点送回原服务的“服务详情”；已保存的变化在该行标记“本次已修改”。若该行已被移除，焦点回到服务表的相邻有效操作。关闭父弹窗恢复镜像列表位置和原“详情”按钮。脚本编辑、删除确认和最终汇总使用当前弹窗内的展开区，不增加第三层业务弹窗。

## 5. 二级弹窗：服务的启动模式

标题示例：“HTTP 服务 · 启动模式”。父弹窗保持可见但不可操作，关闭子弹窗后恢复到原服务行。

### 5.1 模式表

一行对应一个启动模式。建议列：模式名称、启动方式、启动脚本、停止/检查脚本、端口覆盖、默认模式和操作。

模式名称由业务决定，可以是“常规启动”“兼容配置”“只读”“无认证”等，不限于 normal/vuln。它们是同一逻辑服务的可选启动配置，不是镜像 tag，也不是不同的逻辑服务。

操作：新增模式、修改、删除、导入启动脚本、替换脚本、导出文件。文件管理和参数编辑在模式行下方展开，不再叠加第三层业务编辑弹窗。

### 5.2 启动脚本与参数

- 每个模式可以关联一个或多个脚本文件，显示用途、文件名、执行器、工作目录和执行顺序。
- 上传即关联到暂存模式，不立即注册或执行。实际文件身份使用内容摘要校验，不能仅按文件名或大小判断是否变更。
- 脚本可替换、删除、排序、导出；文件内容通过外部编辑后重新导入，不要求填写服务类。
- 启动、停止、就绪检查按各自用途区分，不能把启动进程成功等同于就绪检查通过。
- 执行器按实际镜像能力选择，如按 shebang 执行、sh、bash、python3；不能假设所有镜像都有 bash。
- 仅手动操作模式可不含自动启动脚本；脚本启动模式缺少必需文件时才阻止最终注册。
- 环境变量、参数、依赖和端口均使用行表格；依赖通过服务/模式选择器配置，不输入内部注册名。

复杂既有 CORE 服务实现无法无损转换时，作为实现附件保留并支持整体导入/导出；不把它降级成几项表单后丢掉原有逻辑。

### 5.3 模板选择语义

镜像声明“提供什么”，模板提供默认启用配置，拓扑节点决定本次实际选择。

模板内每个镜像服务一行，使用“是否启用 + 启动模式”控件：未启用时不启动；启用后只能选择该逻辑服务的一个模式。不同服务可同时启用。已有默认模式可预选，但必须可见；没有默认模式时要求明确选择。

全量声明不会把所有服务默认全部勾选。工具环境或不自动启动服务的模板是合法情况。

### 5.4 拓扑节点覆盖与部署冻结

模板保存默认启用服务、每个服务的模式和允许调整的参数。拓扑节点显示配置来源，可选择“使用模板默认”或“自定义此节点”，并提供“恢复模板默认”。同一镜像的两个节点可以分别选择常规启动、演练配置，不需要复制多个模板。

自定义从该节点引用的模板修订复制当前完整选择；之后只改变该节点，不回写模板或其他节点。禁用必须以明确的关闭值表达，不能因缺少字段又继承为启用。恢复默认清除节点覆盖。服务、模式来源只能来自同一镜像的有效目录，原生节点仍限定 CORE 原生目录。

节点固定模板修订和镜像内容标识；模板或服务目录后续更新不会静默改变现有拓扑。升级时展示差异并明确采用新修订，遇到移除模式、无效覆盖或新增依赖时要求处理。运行中的节点修改只能用于下一次运行；启动前将模板修订、节点覆盖、最终有效服务/模式、实现修订与脚本摘要一起冻结到运行记录。

### 5.5 启用组合检查

检查对象是“单个节点本次实际启用的服务与模式”。HTTPD 和 Nginx 都可声明提供 80/tcp；只启用其中一个不冲突，两个不同节点各监听 80/tcp 也不冲突。同一节点同时启用且绑定地址范围重叠才需要阻止，改用其中一个的 8080 模式后可解除冲突。

端口表包含监听地址、协议、端口或范围；模式有覆盖则用覆盖，否则继承服务端口。区分 TCP/UDP、IPv4/IPv6 及实际地址重叠，不把未知端口推断成确定冲突。动态端口、脚本实际监听或复用语义无法静态确认时显示具体警告。跨节点冲突只针对共享的宿主端口等资源单独检查。

依赖由服务/模式选择器声明，展示“缺少依赖服务”“依赖模式不兼容”以及循环路径。可以建议补选依赖，但须用户明确采纳，不能暗中启动额外服务。由实际启用依赖生成确定的启动顺序；出现循环或必需依赖未启用时阻止启动。脚本存在不代表服务就绪，依赖就绪条件另行配置。

模板保存时检查默认组合，拓扑覆盖时检查该节点组合，部署前由后端按冻结配置再次权威校验。镜像清单编辑本身不因为尚未启用的服务端口相同而报错。

## 6. 镜像服务与 CORE 原生服务隔离

仅依靠显示名或前缀猜来源不够，应同时保留机器标识和明确的来源字段。

| 项目 | 镜像服务 | CORE 原生服务 |
| --- | --- | --- |
| 管理归属 | 具体镜像、逻辑服务、启动模式 | CORE 内置/明确归属原生节点的服务目录 |
| 适用节点 | Docker 镜像节点 | netns 等 CORE 原生节点 |
| 用户看到的名称 | HTTP、SSH、Redis 等友好名称 | SSH、DefaultRoute 等原生名称 |
| 机器标识 | 自动生成镜像命名空间中的唯一名字 | 保留原生标识 |
| 来源判断 | 明确 `origin=image` 及所属镜像/服务/模式 | 明确 `origin=core`，不因未带某前缀就自动归为原生 |

内部名字建议采用类似 `imgsvc-<稳定镜像键>-<服务键>-<模式键>-r<配置修订>` 的形式。完整对应关系保存在平台库，名称长度/唯一性由后端处理；界面不要求用户手填前缀。

镜像里的 SSH 和 CORE 原生 SSH 可以同时存在，显示名相同不代表同一个实现。导入文件自带的 CORE 类名也须经过命名空间转换，不能覆盖原生服务。

部署时由平台映射成 CORE 可执行的注册名。运行所需的网络辅助配置单独归属系统层，不冒充镜像软件服务。

旧模式 normal/vuln 可以迁入同一服务的两个模式；旧单模式可以迁为默认模式。无法可靠确定归属的旧条目应在迁移预览中要求确认，不能只截取服务名字符串就强行合并。

## 7. 最后统一确定、注册与 CORE 重启提醒

### 7.1 用户流程

```
编辑镜像服务
  → 子弹窗确定，返回父弹窗暂存
  → 父弹窗确定
  → 父弹窗内展示变更摘要及 CORE 重启提醒
  → 明确确认保存并注册，或仅保存稍后处理
  → 显示逐阶段结果
```

最终确认区列出新增/修改/移除的服务和模式、脚本变化、受影响模板/部署，以及当前所有 CORE 会话数量。提醒范围不能仅限于当前镜像。

按用户要求，本期默认在注册流程中保留统一的重启提醒和明确确认。存在会话时建议阻止直接重启，提供“仅保存、稍后生效”和“返回”；会话处理在拓扑管理完成。没有会话时，用户勾选已了解影响后，按钮才允许“确认保存并注册”。

服务展示名称或备注等不改变执行实现的修改，后台可判定无需注册/重启，并在摘要中说明；不要为每次文字编辑无条件重启。

### 7.1.1 编辑校验与失败保留

编辑中就地提示服务/模式重名、空名称、脚本启动缺文件、无效端口及依赖；无需等到重启确认才看到。未完整的工作副本可继续补齐或仅保存待完善，但不允许注册成功或被新节点选为已生效实现。此阶段的校验不得调用注册或重启接口。

保存失败时保留工作副本和附件引用，显示可重试的失败字段；保存成功但注册失败时显示“已保存，注册失败”，继续使用上次生效配置。展示校验、保存、等待生效、注册、就绪核对各阶段，不能把一个笼统成功提示用于整条流程。重试使用同一变更集与幂等标识，先查询实际进度再继续，避免重复注册；只有全部确认生效才切换新默认目录。

### 7.2 当前代码核对

当前 `core_adapter.activate` 有调用运行中 ServiceManager.load 的通道，已有部署也使用唯一版本名加载服务。**不能笼统断言当前代码对所有新增注册都必须重启。**

但当前安装的 CORE `ServiceManager.add` 会拒绝重名服务；普通 load 也没有完整的覆盖、卸载语义。所以“新增唯一名可动态加载”不等于“同名修改/删除已经可靠生效”。本方案保留用户要求的统一确认与提醒，不用现有热加载入口默默绕过它。

实现阶段应确定哪些变更必须重启、哪些无需重启，以当前安装版本为依据。若未来采用全量唯一名热加载，应另行验证更新、删除和重连一致性，再向用户说明流程变化。

依据：`core_adapter.py::activate`、`topologies.py::deploy_definition`、`/opt/core/venv/lib/python3.10/site-packages/core/services/manager.py::add/load`。本轮只阅读源码，不试验真实注册或重启。

### 7.3 后台处理边界

数据库和守护进程重启不是同一个可原子提交的事务，需要明确阶段：

1. 校验配置修订号、文件、命名空间和引用，生成待应用变更集。
2. 保存配置及不可变实现快照，标记“待生效”，不冒充已经注册成功。
3. 重新核实全部 CORE 会话及任务，协调平台内的新建/启动操作。
4. 由 Bridge 或宿主管理执行器执行必要重启；不能让 CORE 在同步 ExecuteScript RPC 中重启自身。
5. 等待 daemon 就绪，重建连接，读取服务注册结果并逐项核对。
6. 全部通过后显示“已生效”；部分失败保留已保存结果、错误项和重试入口。

仅保存后尚未注册的模式不能在新模板选择中显示成已可执行。旧模板和运行部署继续固定原配置，不被此次编辑暗中替换。

有引用的旧实现允许从新配置中移除，但不能随即抹掉历史执行所需文件。后台继续保留修订和引用关系，前台无需再操作“版本草稿与发布”页面。

CORE 重启可能使运行/定义态会话、终端连接和事件订阅失效，不承诺自动无损恢复。外部 CORE 客户端造成的并发也不能仅靠平台锁消除，实际重启需选择合适的操作窗口。

旧入口链接应跳转至相应拓扑管理视图，不遗失原记录定位。原有 XML 和平台数据文件导入导出继续保留，未知扩展数据应往返保真。

## 11. 实现与迁移建议

本轮不再预设需要新框架才能完成，先稳定上述交互和数据契约。是否采用 Vue/TypeScript 由具体实施方案决定，不作为本次理解确认的门槛。

后端优先增加镜像—逻辑服务—模式的聚合读模型，以及服务配置变更集、脚本附件、命名空间映射和明确的注册应用状态。现有 SQLite、不可变历史、任务回执和引用保护继续复用。

服务清单中的每个模式会对应一个可执行实现。旧版 manifest 中分散的服务条目必须迁移为合适的服务/模式关系，并保留旧注册名的历史映射；不能只改前端表头。

文件选择与子弹窗行保存不调用注册接口。最终确认接口带基准修订号，发生并发修改时展示字段冲突与重新加载入口，不能后写覆盖前写。

节点覆盖需要增加后端数据契约和验证，不能只放开前端控件。建议以模板引用及修订、节点覆盖开关、按稳定服务键记录的启用值/模式/受支持参数，以及冻结后的解析结果保存。当前后端对模板服务集合的一致性约束须同步调整为：在固定来源目录中解析并校验每个节点的有效服务集合，之后再生成 CORE 服务注册名。保留旧拓扑完全继承模板的兼容行为，不允许节点覆盖绕过来源、脚本、依赖及实现修订校验。

导出范围需明确为镜像本体、服务清单、模式及脚本附件或完整交付物。导入多镜像、多标签、多模式时提供表格选择与冲突预览，不静默采用最后一项。

建议分批：

1. 数据契约与旧清单迁移预览，明确服务/模式/来源/脚本的关联。
2. 镜像列表及两级弹窗，支持暂存、增删改、附件导入导出。
3. 最终确认、变更摘要、会话影响提示及受管注册/重启流程。
4. 节点模板默认值、节点独立覆盖、启用组合检查、部署冻结及镜像服务/原生服务隔离。
5. 拓扑管理合并、导入冲突预览/导出范围和所有 JSON 界面替换，保留文件和历史兼容。
6. 按实际受影响范围集中验收，不重复循环跑测试。

## 12. 必要验收场景（后续实施时执行）

- 所有镜像入口统一显示“导入”，普通镜像和空服务镜像可正常管理。
- 镜像详情上方为基本信息，下方服务行可增删改；单个服务能配置多个任意名称模式。

- 导入新增、替换、跳过均有可核对预览；配置与脚本包和完整镜像包范围、缺失项与体积准确。

- 最后确认准确列出增删改与全部受影响会话；不会在脚本上传或行保存时重启。
- daemon 未起来、部分服务加载失败、客户端重连失败时显示真实阶段，不提示全部成功。
- 删除模式不破坏仍被历史或旧模板引用的实现。
- 拓扑所有操作可在拓扑管理中完成，旧入口能定位到迁移后的内容。
- 全页面不再出现 JSON 文本录入、JSON 视图、JSON 备注或原始 JSON 错误倾倒。
- 文件导入导出和 XML/扩展字段往返不丢失内容。
