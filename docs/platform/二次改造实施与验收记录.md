# 管理平台二次改造实施与验收记录

日期：2026-11-17。基线：`cf42836`。对应方案：`管理平台二次改造方案.md` v2.2。

## 已实施的主流程

| 工作项 | 实际行为 |
| --- | --- |
| 镜像与服务模型 | 按镜像完整内容 ID 管理服务清单；逻辑服务包含多个任意名称模式，脚本附件按 SHA-256 保存 |
| 镜像详情 | 原抽屉改为原生弹窗，上方基本信息，下方服务表；服务可新增、编辑、移除声明 |
| 服务详情 | 第二层弹窗编辑模式、执行器、目录、启动参数、环境变量、端口、依赖和启动/停止/就绪检查文件 |
| 旧数据迁移 | 保留原实现和模板附件，旧服务逐项显示；可明确把其他服务的模式移入同一服务，取消不改变原数据 |
| 暂存边界 | 模式确定只回到父弹窗；父弹窗取消放弃本轮修改；变化行高亮，返回原操作焦点 |
| 最后确认 | 最后统一检查、提示 CORE 影响、保存并生效；有会话时保存待生效，不在导入文件或行编辑时注册 |
| 生效与失败 | 保存、生成实现、注册、核对分阶段记录；失败保留配置及上次生效版本，同一未改内容的重试复用待应用版本 |
| 注册隔离 | 镜像实现采用独立修订命名空间；原生目录以 CORE 内置目录判定，不按显示名猜来源 |
| 模板默认 | 模板保存明确的启用服务与模式，绑定已核对注册的镜像配置修订 |
| 节点覆盖 | 节点单独启停服务、选择模式、恢复固定模板默认；模板升级需明确采用，其他节点和旧运行不被改变 |
| 启用组合 | 同节点监听地址、TCP/UDP、端口范围和 IPv6 独占语义检查；服务/模式依赖检查、依赖环检测、启动顺序与就绪脚本 |
| 运行冻结 | 运行记录保存模板/镜像修订、节点覆盖、有效模式与脚本摘要；执行使用已冻结的实现源码，避免随编译器更新重新生成旧行为 |
| 导入 | 镜像/完整交付包从上传或服务器路径接收；服务只进入导入记录，预览后合入工作副本，最后确认才生效 |
| 导入冲突 | 服务级新增、替换、跳过；新增使用新标识并重映射依赖，不静默覆盖同名对象 |
| 导出 | 配置与脚本 ZIP，或带真实镜像的完整 tar.gz；完整包后台处理，任务列表提供下载与重做 |
| 拓扑管理 | 列表、画布、节点/服务、链路/接口、保存、启动停止、运行历史统一管理 |
| JSON 界面替换 | 业务页面移除原始配置填写/查看与高级切换；模板说明为文本，拓扑为字段/表格/文件，运行快照和日志按字段展示 |
| 旧入口 | 旧版本发布页面跳转资源管理；旧草稿 hash 指向拓扑管理；后台历史与兼容接口保留 |

实现主要位于 `image_services.py`、`versions.py`、`target_admin.py`、`topologies.py`、`native_xml.py`、`jobs.py`，前端使用 `static/platform-ui.js` 以及镜像、模板、拓扑三个管理脚本。继续使用现有 FastAPI/SQLite 和 WLGFTY 风格，不额外引入前端框架或生产运行依赖。

## 生效机制与兼容边界

当前安装的 CORE 能加载独立注册名。本轮选择保存不可变修订、加载新名字并核对结果，**没有主动重启 CORE daemon**，也没有增加自动卸载历史实现的操作。最终确认仍保留重启影响提醒；有会话时先保存待生效。该行为与“每次注册都强制重启”不同，依据方案第 7.2 节的实际 CORE 能力取舍。

旧模板/部署固定旧实现，未自动批量转换生产清单，也未改写旧版本。用户打开详情后可确认归并关系并保存新配置。复杂旧服务继续保存原实现附件；导入存在会改变保留服务的附件冲突时明确阻止，要求分件处理，不把任意 Python 实现强行降级成几个表单字段。

仅保存且未生效的模式不会进入新模板的可执行目录。失败版本也不会替代已核对的默认修订。导入文件接收与配置确认分离，父弹窗取消不卸载已经载入的镜像。
