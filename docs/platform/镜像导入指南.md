# 镜像导入与服务配置指南

版本：v2.0，2026-11-17。适用新版镜像管理、节点模板和拓扑管理。

镜像可以是普通应用、工具环境或演练环境，不要求是标靶。清单记录镜像提供的全部服务，实际启用项由模板和拓扑节点选择。无自动启动服务的工具镜像可以保留空清单。

## 1. 导入镜像或完整交付包

进入“镜像管理”，点击“导入”，选择来源与内容：

| 来源 | 镜像归档 | 完整交付包 |
| --- | --- | --- |
| 本机上传 | 选择镜像 tar | 选择 tar.gz |
| 服务器路径 | 填写镜像归档路径 | 填写交付内容所在目录 |

完整包的镜像本体文件名为 `image.tar`。新版完整包还包含配置和脚本；旧 `manifest.json`、`services/*.py` 和 `services/templates/` 结构继续接收。

上传后由后台加载镜像，可在“导入任务”查看阶段；失败或中断使用“续办”，需要时补充镜像路径。接收配置不等于注册成功，完成后打开镜像详情预览并合入内容。取消服务编辑不会卸载已经载入的镜像。

## 2. 镜像详情：基本信息与服务清单

详情为弹窗。上方显示镜像标识、标签、平台、大小、目录及配置状态；下方一行一个服务。

- “新增服务”填写名称、软件版本、用途和端口。
- “编辑”更正服务信息。
- “移除声明”只移除该条目及其模式，不卸载软件，不直接停止已有节点。
- “详情”进入该服务的启动模式弹窗。

暂时不运行某个服务时，保留声明，在模板或节点取消启用，不为停用而删掉完整清单。

## 3. 服务详情：启动模式与脚本

服务可以配置“常规启动”“备用端口”“兼容配置”“手动维护”等模式，不限定 normal/vuln。节点每次只选择该服务的一个模式，不同服务可以同时启用。

模式可设置执行器、工作目录、启动参数、环境变量、监听端口覆盖、依赖服务及依赖模式。选择用途后导入启动、停止或就绪检查脚本；文件可以移除、排序和导出。同名同用途文件在本轮修改中替换，摘要区分内容。文件在外部编辑后重新导入，不要求填写服务类或配置文本。

脚本启动模式必须有关联的启动文件；“仅手动操作”可以没有。脚本应正确处理后台进程和输出重定向，避免永不退出的前台进程阻塞启动。判断真正就绪时，另加就绪检查脚本。

旧独立服务条目可以用“将旧模式合并到此服务”明确归组；来源没有剩余模式时，确认后移除其空声明。原实现和历史修订保留，不按名字自动猜分组。

二级“确定”只暂存回镜像详情，“取消”只撤销该服务的本轮编辑；返回原服务操作，已修改行高亮。

## 4. 最后统一确定

镜像详情的“确定”进入本弹窗内的最终汇总，显示变化、待完善项、引用和阻塞注册的 CORE 会话。

- “返回修改”继续编辑。
- “仅保存，稍后生效”保留配置，不替换上次生效实现。
- “确认保存并生效”需要配置完整、了解注册与重启的影响，且没有正在配置、启动、运行或停止的 CORE 会话。已停止的会话可以保留。

当前采用独立修订名加载并核对结果。遇到会话阻塞时，可以先保存待生效，并从确认页打开对应会话，在拓扑管理中停止后再确认。

失败会显示处理阶段，保留已保存内容与上次生效版本。修正后继续确认，不必重输整个清单。上传、行保存和子弹窗确定均不直接注册。

## 5. 在模板与拓扑中使用

1. 在“节点模板”选择 Docker 镜像及已生效配置修订。
2. 在服务表用“启用 + 模式”设置默认值；全量清单不会全部默认启动。
3. 保存模板，在“拓扑管理”添加模板节点。
4. 节点选择“自定义此节点”可独立启停服务与选择模式。
5. “恢复模板默认”只恢复当前节点引用的固定修订，不改变其他节点。
6. 检查端口、依赖和顺序，保存后启动；运行记录保存本次实际配置。

镜像 SSH 与 CORE 原生 SSH 来自不同目录。Docker 节点选所属镜像服务，原生节点选 CORE 原生目录，界面不要求填写内部注册前缀。

两个节点各监听 80/tcp 不冲突；同节点启用两个绑定重叠地址和端口的服务时需调整。仅在清单中同时声明 HTTPD 与 Nginx 不报冲突。

## 6. 配置导入与交付导出

详情的“导入清单”选择配置文件或配置与脚本 ZIP。预览按服务选择新增、替换、跳过；替换包含该服务全部模式与脚本，新增同名服务须先改名称。合入后仍需最后确认。

“导出当前配置与脚本”包含编辑副本及附件，可在取消或处理并发冲突前留存。列表“导出”有两种范围：

| 范围 | 内容 |
| --- | --- |
| 配置与脚本 | 镜像标识、服务、模式、依赖、参数及脚本，不传输镜像本体 |
| 完整镜像包 | 以上内容及真实镜像，后台打包 |

在导出弹窗或“完整包导出任务”表下载。失败显示原因并可重新导出，不把缺少镜像本体的包提示为完整成功。

## 7. 运行范围与常见问题

导入/管理镜像不代表该镜像必然能作为 CORE 节点运行。实际运行仍需满足当前 CORE/Docker 的保活、命令通道、文件投递和软件环境要求。模式执行器需与已有工具一致；选择 sh 不会自动补齐 CORE 容器通道需要的其他工具。

脚本单文件上限 2 MiB，配置导入包 32 MiB；大镜像通过归档或完整包入口导入。当前没有浏览器断点续传。

镜像详情没有“独立容器验证”入口或必经步骤。“容器管理”仍独立保留；真正的节点运行和模式结果在拓扑管理检查。

详细验收范围及尚未开放的参数覆盖等能力，见《二次改造实施与验收记录》。旧教程移至 `archive/镜像导入指南-v1.md`，不再作为当前步骤。

## 8. 服务/工具判定口径与已知坑（2026-11-17 实测补充）

> 来源：CSLE 风格基底镜像（target-csle-base:v1）按本指南全流程构建导入实测。详细版见工作目录《镜像导入指南》（§2.5 判定口径 + 22 条坑速查表）。

**清单只登记服务，工具不登记**。服务 = 可声明启停 + validate 可校验的持续能力（守护进程型如 httpd/sshd；配置动作型如 DefaultRoute/svc-forward——持续生效的内核状态也算）。工具 = 用完即走的 CLI：操作手段类（nmap/curl/nc）不登记；运行时依赖类（iproute2/iptables）不登记但**镜像必须装**——CORE 配接口用宿主 `ip`（`nsenter -n`）不受影响，而服务 startup 命令跑在容器 mount ns（`nsenter -m`），缺了直接失败。分界线：同一命令手敲 = 一次性操作；被声明 startup + validate = 服务。客户端包（snmp/smbclient）、二进制变体（nginx-debug）、子系统（sftp-server）、运行时能力（python3 -m http.server）都不算服务。

**本轮实测已修的平台缺陷**（commit 同步，上游可复核）：

| # | 缺陷 | 修复 |
|:--|:--|:--|
| 1 | 预检 L2 用 `shell=False` 执行 validate——目录模型生成的 validate 含 shell 语法（`cd / && sh ...`）→ rc=127 全量假报 missing | `node_command(..., True, True)`（target_admin.py run_validate） |
| 2 | 预检 L3 端口匹配：清单条目名 `imgmode-*` 与启用名 `imgsvc-…-imgmode-*` 后缀不对齐 → 端口永远探测不到 | 按后缀对齐匹配（target_admin.py L3） |

**仍有待上游处理的坑**：旧模板迁移用 `mode_name()`（imgmode 名）匹配旧式 `svc-*` 声明名永远不中 → 模板被静默清空服务（services=[]、selection={}，部署出无服务容器）；现用显式 `service_selection` 重存模板触发重发布兜底。修复方向：legacy 模式按 `mode['implementation']` 原名匹配。另：commit apply 存在任意活跃会话时自动降级"保存待生效"（设计如此，apply 前确认 `GET /api/sessions` 为空）。
