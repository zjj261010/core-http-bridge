# 靶标镜像导入指南

> 版本：v1.0（2026-11-15）
> 适用平台：CORE 9.2.1 + core-http-bridge（五 Tab 管理平台）
> 架构前提：路线 B（镜像不自启服务，CORE 声明启动）+ 三件独立导入 + 无验证门禁
> 本文所有规范均来自本项目实测教训，每条坑都有对应的事故背景（见 §10 坑速查表）

---

## 1. 概述：要准备什么

导入一个靶标镜像 = 导入一套**靶标包（三件套）**。**镜像必须导入；服务定义和配方清单可缺、缺件进详情抽屉补录**（用户定稿 2026-11-15）。

入口只有一个：**「导入靶标包 ▸」**，两种模式：

**模式 A 整体导入（推荐）** —— 服务器上一个目录含三件（包名=目录名）：

```
/opt/artifacts/core-drill/image-imports/<包名>/
├── image.tar        ① 基座镜像（★必须——缺它整包判失败）
├── services/        ② 服务定义（*.py + templates/ 整树，可缺）
│   └─ templates/
└─ manifest.json    ③ 配方清单（可缺——详情抽屉补录）
```

UI：填目录 → 导入 → 三件落位表（✓ 就位 / ✗ 失败）。
API：`POST /targets/import/bundle {"dir": "<目录>"}`。

**模式 B 分开导入** —— 镜像 tar **必填**，服务定义（包名+.py 内容）和 manifest JSON 可选，一次提交分别落位。
API：`POST /targets/import/pieces {"image_path"(必填), "package"?, "py"?, "templates"?, "manifest"?}`。

三件落位后，缺的服务定义/清单在**详情抽屉**补录（清单 JSON 编辑器 + 服务定义 .py 补录区）。注意：镜像未导入则整个靶标条目不存在（列表只显示已导入镜像）——不存在"先编目后补镜像"的状态。

| 件 | 内容 | 作用 | 缺了会怎样 |
|:--|:--|:--|:--|
| ① 基座镜像 | `xxx.tar`（docker save 产物） | 软件与配置装好的容器文件系统 | 无法部署节点 |
| ② 服务定义 | `service.py` + `templates/*.sh` | 告诉 CORE 怎么启动服务（normal/vuln 成对） | 无法声明启动服务（节点起了但没服务） |
| ③ 配方清单 | `manifest.json` | 编目：软件/版本/CVE/端口/服务绑定 | 镜像显示"未编目"，无端口级预检 |

准备工作的核心认知：**镜像里装软件但不启动软件**。启动方式由服务定义声明，启动哪份（normal/vuln）由想定决定，运行中冻结。

## 2. 第一步：构建基座镜像

### 2.1 镜像规范（路线 B 硬约束）

| 要求 | 原因 |
|:--|:--|
| `WORKDIR /`（必须） | CORE 投递服务文件用相对路径；继承官方镜像的 WORKDIR（如 httpd 的 `/usr/local/apache2`）会导致服务文件落盘失败 |
| **不写 CMD / ENTRYPOINT** | CORE 启动容器用 `tail -f /dev/null` 覆盖保活，镜像 CMD 永远不会执行；写了会造成"自启假象" |
| `USER root` | 服务投递（docker cp + chmod）需要 root |
| 装 `iproute2 procps curl netcat-openbsd` | ip=预检与人工排障；procps=pidof/ps（validate 命令依赖）；curl/nc=连通性测试 |
| 双模式配置**装进同一镜像** | normal/vuln 共用基座，只差配置文件（如 `secure.conf` / `vuln.conf` 两份），由服务定义选择——避免镜像变体爆炸 |
| 软件装好但**不启动** | 路线 B 核心：启动由 CORE 声明完成 |

### 2.2 示例 Dockerfile（httpd 2.4.49 + CVE-2021-41773 双模式）

```dockerfile
FROM httpd:2.4.49
USER root
RUN sed -i 's|deb.debian.org/debian|archive.debian.org/debian|g' /etc/apt/sources.list && \
    apt-get -o Acquire::Check-Valid-Until=false update -qq && \
    apt-get install -y -qq --no-install-recommends curl netcat-openbsd iproute2 procps && \
    rm -rf /var/lib/apt/lists/* && \
    # 双模式: 复制一份配置改成有洞版
    cp /usr/local/apache2/conf/httpd.conf /usr/local/apache2/conf/httpd_vuln.conf && \
    printf '\nLoadModule cgid_module modules/mod_cgid.so\nScriptAlias /cgi-bin/ /usr/local/apache2/cgi-bin/\n<Directory "/">\n    Options +ExecCGI\n    Require all granted\n</Directory>\n' >> /usr/local/apache2/conf/httpd_vuln.conf && \
    echo 'ServerName localhost' >> /usr/local/apache2/conf/httpd.conf
WORKDIR /
# 无 CMD/ENTRYPOINT —— CORE 用 tail -f /dev/null 保活, 服务由声明启动(路线 B)
```

### 2.3 构建环境网络注意事项

- 老发行版源（如 buster）已进 `archive.debian.org`，需先 sed 改源并加 `-o Acquire::Check-Valid-Until=false`
- 新发行版用国内镜像源（debian 12 的 sources 在 `/etc/apt/sources.list.d/debian.sources`）
- 构建完成后导出：`docker save -o /opt/artifacts/core-drill/image-imports/<镜像名>.tar <name>:<tag>`
- tar 放服务器本地路径（导入接口按**服务器路径**读文件，不走浏览器上传）

### 2.4 命名规范

```
平台自建: target-<位置>-<软件>-<CVE>:<版本>    如 target-dmz-base:v3 / target-inn-base:v3
通用简洁式: target-<角色>:<版本>              如 target-attacker-kali:v1 / target-fw:v1
```

## 3. 第二步：编写服务定义（.py + templates/）

### 3.1 目录结构（CORE 约定）

```
/opt/core/etc/custom_services/<包名>/
├── __init__.py          # 空文件
├── service.py           # CoreService 子类
└── templates/           # ★ 必须是这个子目录名, 平铺会投递失败
    ├── xxx-normal.sh
    └── xxx-vuln.sh
```

### 3.2 service.py 模板

```python
from core.services.base import CoreService


class SvcHttpd41773Normal(CoreService):
    name: str = "svc-httpd-41773-normal"      # ★ 注册名（想定/manifest 用的是它, 不是类名）
    group: str = "Drill"
    files: list[str] = ["httpd-normal.sh"]     # 对应 templates/httpd-normal.sh
    startup: list[str] = ["bash httpd-normal.sh"]
    validate: list[str] = ["pidof httpd"]      # ★ A1 预检 + CORE 启动校验都用它
    shutdown: list[str] = ["pkill httpd"]
    # ★ 不要写 executables —— CORE 在宿主机 PATH 上校验, 容器独有二进制(httpd等)会注册失败


class SvcHttpd41773Vuln(CoreService):
    name: str = "svc-httpd-41773-vuln"
    group: str = "Drill"
    files: list[str] = ["httpd-vuln.sh"]
    startup: list[str] = ["bash httpd-vuln.sh"]
    validate: list[str] = ["pidof httpd"]
    shutdown: list[str] = ["pkill httpd"]
```

### 3.3 启动脚本模板（templates/xxx.sh）

```bash
#!/bin/bash
# normal: 出厂配置启动（无洞）
httpd -DFOREGROUND >/dev/null 2>&1 &
```

```bash
#!/bin/bash
# vuln: 有洞配置启动（漏洞可达）
httpd -DFOREGROUND -f /usr/local/apache2/conf/httpd_vuln.conf >/dev/null 2>&1 &
```

**铁律：后台进程必须 `>/dev/null 2>&1 &`。** 不重定向会让进程继承 CORE exec 的管道，CORE 等管道关闭 → `start_session` 永久阻塞（本项目踩过的最重的事故之一）。

### 3.4 命名规范（正式）

```
服务名 = svc-<软件>-<CVE或能力>-<模式>
  模式 ∈ {normal, vuln}     成对注册、同软件互斥（想定声明二选一）
validate = 跑得通且能证明服务在的最小命令（通常 pidof <真实进程名>）
```

注意 pidof 的进程名必须与**实际进程名**一致：redis 的守护进程名是 `redis-server` 不是 `redis`；nginx 是 `nginx`。

### 3.5 导入方式

单文件 UI 上传（Tab1 → 导入服务定义，选 .py）；带 templates 的完整包走 API：

```bash
curl -X POST http://<host>:8080/targets/import/services -H 'Content-Type: application/json' -d '{
  "package": "my-drill",
  "py": "<service.py 全文>",
  "templates": {"xxx-normal.sh": "<脚本全文>", "xxx-vuln.sh": "<脚本全文>"}
}'
```

落到 `/opt/core/etc/custom_services/<包名>/`。

## 4. 第三步：编写 manifest（配方清单）

### 4.1 Schema

```json
{
  "name": "dmz-httpd-41773",
  "software": "httpd",
  "version": "2.4.49",
  "cve": ["CVE-2021-41773"],
  "image": {
    "name": "target-dmz-base",
    "tag": "v3",
    "ports": [80]
  },
  "services": [
    {"name": "svc-httpd-41773-normal", "mode": "normal"},
    {"name": "svc-httpd-41773-vuln", "mode": "vuln"}
  ],
  "flags": [],
  "notes": "httpd 路径穿越 RCE 双模式靶标"
}
```

### 4.2 字段约束（错一处就缺件）

| 字段 | 约束 | 校验方 |
|:--|:--|:--|
| `name` | 必填，manifest 主键 | 导入接口 |
| `image.name` + `image.tag` | 必须与 docker 镜像 ref 精确对应（`name:tag`），这是清单绑定镜像的锚 | 三件完整性 |
| `image.ports` | 端口级预检（A1）的探测依据；也可写在顶层 `ports`（两种写法兼容） | A1 预检 |
| `services[].name` | 必须与 service.py 里 `name` 字段**逐字符一致**（不是类名！） | 三件完整性 |
| `services[].mode` | `normal` / `vuln`；同软件两模式只能出现在两个服务里（互斥校验在实例层） | Tab3 |

## 5. 第四步：导入操作

### 5.1 UI 路径（左侧导航 → 镜像管理）

1. **导入镜像**：右上角按钮 → 填服务器 tar 路径（如 `/opt/artifacts/core-drill/image-imports/target-xxx.tar`）→ 导入（大镜像需数十秒到数分钟）
2. **导入服务定义**：右上角按钮 → 选 .py 文件（仅单文件；带 templates 走 API §3.5）
3. **编目**：点镜像行「详情」→ 底部 manifest 编辑器已生成骨架 → 填 software/cve/ports/services → 保存清单
4. 列表行出现绿色「已编目」标记，三件完整性转绿

### 5.2 API 路径（等价）

```bash
# ① 镜像
curl -X POST http://<host>:8080/targets/import/image -H 'Content-Type: application/json' \
  -d '{"path": "/opt/artifacts/core-drill/image-imports/target-xxx.tar"}'

# ② 服务定义（见 §3.5）
# ③ 清单
curl -X POST http://<host>:8080/targets/manifest/dmz-xxx -H 'Content-Type: application/json' \
  -d '{"manifest": { ... §4.1 的 JSON ... }}'
```

### 5.3 导入后的快速自检

```bash
curl -s http://<host>:8080/targets | python3 -m json.tool   # 看 pieces 三件状态
```

## 6. 第五步：重启 core-daemon（服务注册生效）

服务定义导入后，**必须重启 core-daemon 才会注册**（CORE 只在启动时扫描 custom_services 目录）：

```bash
systemctl restart core-daemon
```

⚠️ **维护窗口操作**：
- 重启 daemon 会**杀掉所有运行中的会话**（容器销毁、drill 标记 interrupted）
- bridge（core-bridge.service）不需要重启——它独立于 daemon
- 重启后平台采样线程会自动把孤儿 drill 标为 interrupted、为 live 会话补登记

## 7. 第六步：验证链（导入质量把关）

按顺序四步，全绿才算导入完成：

```
① 三件完整性   GET /targets → dmz 靶标 pieces.complete = true
② 独立容器验证  Tab2 新建容器（选该镜像；**启动命令填 `tail -f /dev/null`**——路线 B 镜像无 CMD）
   → exec 手动跑服务命令 → 确认能启动、配置切换符合预期
③ 实例化验证    Tab3 建实例（绑定镜像+服务对）→ 画布拖入 → 启动会话
④ A1 预检      画布工具条「🩺 预检」→ READY
               （服务 validate ok + 编目端口 open；NOT_READY 时按提示修）
```

预检能抓住的典型错误：服务名与注册名不符、镜像里缺软件（validate missing）、服务没启动（端口 closed）。预检动作自动入审计（audit 表）。

## 8. 外源镜像路径（无编目起步）

外源/第三方镜像完全支持，流程是"先导入、后补录"：

```
① 只导镜像 tar → 列表显示「未编目」（合法状态）
② Tab2 起独立容器（普通隔离）→ exec/终端摸底：
   装了什么软件、监听什么端口、服务怎么启动
③ 手动补录 manifest（详情抽屉的编辑器有骨架可改）
④ （可选）为它写服务定义对 → 走 §3/§6
⑤ A1 预检按声明范围自动工作：
   - 声明了服务 → 存活 + validate 全查
   - 什么都没声明 → 仅容器存活检查 + 标注"未编目，仅完成存活检查"
   - 想要端口级预检 → 补 manifest.ports 即可
```

平台不探测镜像内容；预检的检查项全部来自你自己的声明（服务声明 + 编目端口）。

## 10. 已知坑速查表（全部实测事故）

| # | 坑 | 症状 | 规避 |
|:--|:--|:--|:--|
| 1 | 镜像写 CMD 自启 | 服务永远不启动（CORE 用 tail 覆盖 CMD） | 镜像不写 CMD/ENTRYPOINT |
| 2 | WORKDIR 不是 / | 服务文件投递后 chmod 报 No such file | 基座镜像 `WORKDIR /` |
| 3 | 服务定义写 executables | 服务注册失败（CORE 在宿主 PATH 校验，容器独有二进制找不到） | 删掉 executables 字段 |
| 4 | 模板平铺在包目录 | 模板投递失败 | 必须放 `templates/` 子目录 |
| 5 | 启动脚本后台进程不重定向 | start_session 永久阻塞（exec 管道不关） | `>/dev/null 2>&1 &` |
| 6 | manifest 写类名（DmzVuln） | 三件完整性 services 缺件、预检 unknown | 写注册名 `name` 字段值 |
| 7 | pidof 进程名写错（redis vs redis-server） | 预检假报 missing | 用 `ps` 确认真实进程名 |
| 8 | 老发行版 apt 源失效 | 构建失败 | archive.debian.org + Check-Valid-Until=false |
| 9 | 镜像加速器别名重复 | 列表出现同镜像多行 | 平台已按 image ID 去重别名 |
| 10 | 重启 daemon 不在维护窗口 | 正在跑的演练全部被杀 | 维护窗口操作，演练前完成导入 |
| 11 | manifest ports 位置写错 | 预检不探测端口（已兼容两种写法） | 优先写 `image.ports` |
| 12 | 无 CMD 镜像在 Tab2 独立容器验证 | 容器立即退出（docker run 没有 CORE 的 tail 保活覆盖） | 新建容器时启动命令填 `tail -f /dev/null`，再 exec 验证 |
| 13 | docker build 报 containerd-mount unmount busy | 构建在导出层时失败（偶发） | 直接重试构建即可；勿重启 docker（会杀掉运行中的容器） |
| 14 | pkill/pgrep -f 匹配到验证命令自身 | exec 的 bash 被误杀，输出缺失 | 换不含自身命令行特征的匹配串 |
| 15 | **validate 用 `pgrep -f xxx` 自匹配假阳性** | 服务没起 validate 也报 ok（pgrep 匹配到检查命令自身的命令行） | 首选 `pidof <进程名>`；必须用 pgrep -f 时加括号技巧：`pgrep -f '[s]erver.py'` |
| 16 | **validate 命令依赖的工具镜像里没有** | validate 报 error（如 nginx:stable 无 pgrep/ps） | 写 validate 前先进容器确认工具存在（Tab2 独立容器 `which pidof pgrep`） |
| 17 | 刚实例化就预检报端口 closed | 服务进程在但尚未完成端口绑定（慢机器） | 平台预检已内置宽限重试（`wait` 参数默认 8s）；CLI 自测时等几秒再探 |
| 18 | CORE 内 netcat 是 **openbsd 变体**，语法与传统 netcat 不同 | `nc -l -p 9999`（listen 不带 -p）和 `nc -q 3`（无此选项）都直接失败，流量测试无数据 | 监听用 `nc -l <端口>`；发送端 `dd if=/dev/zero bs=1K count=80000 2>/dev/null \| nc <对端IP> <端口>`（EOF 后靠对端 timeout 收尾） |

## 11. 导入前检查清单

```
镜像
 □ WORKDIR /
 □ 无 CMD/ENTRYPOINT
 □ iproute2 procps curl nc 已装
 □ 双模式配置文件都已放进镜像
 □ docker save 导出 tar，放在服务器持久目录（/opt/artifacts/...）

服务定义
 □ 成对（normal + vuln），命名 svc-<软件>-<CVE>-<模式>
 □ templates/ 子目录结构
 □ 启动脚本后台进程已重定向
 □ validate 用真实进程名
 □ 无 executables 字段

manifest
 □ image.name/tag 与 docker ref 一致
 □ services[].name 与 service.py 注册名逐字符一致
 □ ports 已填（要端口级预检的话）

操作
 □ 三件都已导入（/targets 看 pieces）
 □ core-daemon 已在维护窗口重启
 □ 验证链四步全绿（完整性 → 独立容器 → 实例化 → 🩺 READY）
```
