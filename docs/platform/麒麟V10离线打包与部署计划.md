# 麒麟 V10 离线打包与部署计划

本方案适用于已通过旧离线包安装 CORE 的麒麟 V10 x86_64 主机。现场系统 Python 为 3.8，glibc 为 2.28。Bridge 部署在 CORE 所在宿主机，复用现场 CORE 使用的独立 Python 3.10，在自己的虚拟环境中安装 Bridge 和匹配的 CORE SDK。系统 Python、glibc 和已安装的 CORE 沿用现场配置。镜像、模板、拓扑和运行记录继续在本机使用，导入导出也在本机完成。

## 现场基线

旧 CORE 离线包记录包含 CORE 9.2.1 和独立的 Python 3.10.15，记录中的解释器路径为 `/opt/python310/bin/python3.10`。打包时以现场 `core-daemon` 实际使用的解释器和 SDK 为准。若现场 CORE 版本与当前仓库已验收的 9.2.1 不同，先验证 SDK 和守护进程的兼容性，再锁定依赖。若现场缺少可复用的 Python 3.10，则在环境补充包中提供独立解释器。[当前运行环境](../../README.md) · [Bridge 依赖清单](../../requirements-linux-x86_64-py310.txt)

| 采集项 | 用途 |
| --- | --- |
| 麒麟产品、版本和补丁级别、CPU 架构、glibc、RPM 或 DEB 包系 | 选择构建机、系统包来源和动态库基线 |
| CORE 版本、systemd 单元及运行用户、实际 Python 路径、CORE SDK 及 gRPC 相关依赖版本、gRPC 地址 | 确定 Bridge 的 Python 环境和连接配置。默认 gRPC 地址为 `localhost:50051` |
| Docker 引擎和 CLI、现有镜像架构、`nsenter`、`ss`、`timeout`、`stdbuf` | 确定环境补充包的缺项及容器拓扑的验收条件 |
| Bridge 当前单元和配置、数据库和附件路径、CORE 服务目录、磁盘剩余空间 | 确定安装、备份和回滚位置。初装时确认目录、权限和空间 |

可使用以下只读命令开始采集。CORE 单元名以现场为准，解释器版本从该单元的实际启动入口核对。

```bash
cat /etc/os-release
uname -m
getconf GNU_LIBC_VERSION
systemctl show core-daemon -p FragmentPath -p ExecStart -p User
command -v rpm dpkg docker nsenter ss timeout stdbuf
```

## 包件与内容

| 包件 | 内容 | 使用条件 |
| --- | --- | --- |
| Bridge 主包 | 固定 Git 提交的程序、前端及 Swagger 静态资源、完整 Python wheel 仓库及哈希锁定清单、systemd 模板、预检、安装与回滚工具 | 必装。包含 HTTP 背景流量功能 |
| 网络工具包 | iperf3、Snort 3、LibDAQ 和 pcap 模块、所需私有动态库、Snort 配置和一套验收规则 | 启用 TCP/UDP 背景流量或 Snort 告警时安装 |
| 环境补充包 | 经现场盘点确认缺少的 Python 3.10、Docker 或系统依赖，以及按需提供的 x86_64 验收镜像归档 | 按缺项制作，按组件安装。系统包来自匹配现场版本和包系的仓库，带齐依赖 |

每次交付附包件版本、Git 提交、适用系统版本、构建环境、软件版本和来源、包件大小、SHA-256 校验清单及安装顺序。部署凭据使用现场私有配置。生产数据、业务镜像及既有规则由现场保管，通过现有入口按需导入。

## 联网制作

1. **固定 Bridge 源码与依赖。** 以仓库依赖清单为基础，补齐现场 CORE SDK 和整个依赖闭包，生成带哈希的正式锁定清单。收集纯 Python wheel 及兼容 CPython 3.10 的二进制 wheel。对 x86_64 二进制 wheel，选择 glibc 基线不高于 2.28 的构建，并核实动态库依赖。缺少合适 wheel 时，在目标兼容环境构建 wheel。最终在相同基线的断网环境验证全量安装。[Python wheel 平台兼容规范](https://packaging.python.org/en/latest/specifications/platform-compatibility-tags/)
2. **为麒麟构建网络工具。** 以项目已验收的 iperf3 3.22、Snort 3.13.2.0、LibDAQ 3.0.29 为起点。当前 WSL 上三者的二进制都引用 `GLIBC_2.34` 符号，应在与现场同版的麒麟构建机重建。检查可执行文件、DAQ pcap 插件及传递依赖的 GLIBC、GLIBCXX 和其他运行库要求。将需随包分发的库放进工具私有目录，发布前验证 iperf3 的 `--json-stream` 和 Snort 的配置检查、pcap 抓包、JSON 告警输出。[项目网络工具配置](../../README.md#背景流量与-snort-预警)
3. **准备辅助包件。** 若需补齐 Python，验证独立解释器可创建虚拟环境并能使用 SSL、SQLite 和 SQLite JSON 函数。若需补齐系统包，下载匹配现场补丁级别的包及依赖。验收容器选用普通 HTTP 服务镜像，确认 `linux/amd64` 并生成本地归档。[Docker 镜像归档命令](https://docs.docker.com/reference/cli/docker/image/save/)
4. **在独立的断网麒麟环境试装。** 使用从现场基线重建的虚拟机，预装同版 CORE。阻断互联网访问，保留本机与验收所需内网连通性。只用交付包完成安装、断网验收和回滚演练。记录缺项，补齐后形成正式发布包和验收记录。

## 现场安装与升级

建议将版本化程序和虚拟环境放在 `/opt/core-http-bridge/releases/<版本>/`，按最终绝对路径创建虚拟环境。systemd 的启动命令和工作目录应指向同一版本。网络工具沿用 `/opt/core-network-tools` 的目录结构，安装到独立目录时通过 `CORE_BRIDGE_NETWORK_ROOT` 指定。业务数据沿用 `/opt/artifacts/core-drill` 或现场已配置路径，安装包及交付记录保存在持久目录。

1. **预检并暂存。** 校验包件 SHA-256，核对系统与现场基线。检查 SDK 和 gRPC 连通性、业务目录和 CORE 共享目录权限、磁盘空间、运行中的会话和导入任务。需要补充组件时，在启用新 Bridge 前先处理缺项。
2. **安装到新版本目录。** 用现场确认的 Python 3.10 创建独立虚拟环境。安装器使用本地 Python wheel 仓库，并在切换前检查依赖、模块导入、Swagger 资源和 SQLite。现有 `scripts/offline-check.py` 可作基础检查，其读取的版本清单须与实际交付一致。真实 CORE 连通性、Docker 守护进程、SQLite JSON 功能和网络工具运行能力另做实际预检。[现有预检脚本](../../scripts/offline-check.py)

   `<版本目录>` 和文件名按正式发布包填写。正式锁定清单应包含所有传递依赖及其哈希。

   ```bash
   "<版本目录>/.venv/bin/python" -m pip install \
     --no-index --find-links "<版本目录>/wheels" --require-hashes \
     -r "<版本目录>/requirements.lock.txt"
   "<版本目录>/.venv/bin/python" -m pip check
   ```

3. **备份并切换。** 在维护窗口等导入和运行任务结束。使用 SQLite backup API 或项目备份脚本保留一致的数据库副本，并备份当前 systemd 配置及本次会改动的规则、附件和 CORE 服务定义。备份存入 `/var/backups/core-http-bridge/<发布批次>/`。切换到新版本后启动 Bridge，检查健康接口、服务日志和真实 CORE 会话读取，再开放业务写入。Bridge 的版本切换只需重启 Bridge 服务。[备份与恢复](部署与回滚.md)
4. **按原版本恢复。** 启动、迁移或关键功能验收失败时，停新 Bridge，留存本次日志及当前数据副本，恢复上一版程序、配置和与其匹配的数据库及受影响附件，然后启动旧 Bridge 并复查。初装失败时恢复安装前的服务配置和原有文件。开放业务写入后再回滚，需要先保全切换后的数据。

## 断网验收

在独立的断网麒麟环境完成全表验收。到现场后，按启用的组件核查对应功能并留存结果。验收使用测试会话、镜像和规则，结束后清理测试资源。

| 项目 | 通过条件 |
| --- | --- |
| 基础启动 | `pip check` 及版本检查通过。SQLite JSON 函数和空库初始化正常。管理页面、`/docs` 和 `/openapi.json` 在断网环境可用 |
| 真实 CORE | `/health` 返回正常且会话数量与 CORE 一致。创建、启动、停止原生节点测试拓扑，记录可以回看 |
| Docker 拓扑 | 通过平台导入本地 x86_64 测试镜像，选用容器模板部署全 Docker 拓扑并验证节点间连通。停止后测试容器正常清理 |
| 背景流量 | 从原生及全 Docker 拓扑分别运行 HTTP、TCP 和 UDP。HTTP 有成功请求，TCP/UDP 有实际速率数据，停止拓扑后任务结束。未安装网络工具时验收 HTTP |
| Snort | 导入普通流量验收规则，在原生及全 Docker 拓扑监听选定接口，观察实际捕获和告警，验证列表与导出。停止拓扑后探针退出 |
| 数字平台 V2 | 数字平台暂缺时用本地客户端验收，并关闭 `BRIDGE_VALIDATION_MOCK`。通过普通服务检查验证 Q1 状态、Q2 结果和 Q3 告警查询。验收覆盖查询接口与真实 CORE，双方系统联调另行安排。[V2 接口契约](../design/数字平台与容器平台交互设计V2.0-查询模式.md) |
| 持久化与回滚 | 重启 Bridge 后，镜像、模板、拓扑和历史仍可读取。有上一版本时，从备份恢复后版本和数据匹配，原有 CORE 正常运行 |

## 发布条件

正式发布前确认现场麒麟版本及包系、CORE 使用的 Python 和 SDK 版本，并留存校验清单、断网安装记录、功能验收结果和回滚记录。当前已核对项目依赖与 WSL 网络工具的 glibc 要求，现场基线、正式包件和麒麟断网验收待完成。

## 升级场景与实测结论（2026-11-24 补记，容器平台侧核对）

**现场基线确认**：目标现场已通过旧离线包安装 CORE 9.2.1 + 拓扑版 Bridge（v1.1.5）＋可用 Python 3.10 环境。本计划按**升级场景**执行——初装支路（补 Python 3.10、从头建依赖）降级为附录，仅在 venv 损坏时启用（`install.sh --fresh`）。

**实测结论**（本机构验证，2026-11-24）：

1. **零新增依赖**：v1.1.5 之后全部新增模块（验证序列/镜像资产/数据库层等）仅使用标准库＋现场已有依赖栈——升级默认**不动现场 venv**，只做版本核对（`install.sh` 升级模式内建核对，差异仅提示）。
2. **wheel 基线兼容**：二进制 wheel 全部可按 `manylinux_2_17`（glibc≥2.17）口径取到——主包 wheel 仓库**不需要麒麟构建机**，已在 `bridge-v1.2-7f8ed0a` 落实并完成全新 venv 实装验证（`pip check`/`offline-check`/启动冒烟全过）。
3. **依赖闭包修订**：原清单缺 CORE gRPC SDK 硬依赖（protobuf/netaddr）与 CORE 安装器闭包（Mako/fabric/invoke/lxml==5.2.2/pillow/pyproj 等），按现场基线重锁并补齐——`lxml==5.2.2` 为 CORE 既定版本，禁止升级；PyYAML 钉 core 声明的 6.0.1（现场 6.0.3 属历史漂移）。
4. **systemd 模板**已入库 `deploy/core-bridge.service`（环境变量全可选：Token/回调/mock 均为 opt-in，默认拉模式免鉴权）。

**包件状态**：主包/镜像导入包（15 个，含漏洞标注）/镜像散件/Snort 规则附件已就绪——清单与校验见交付目录《交付总清单.md》。**唯一待外部条件**：网络工具包需麒麟 V10 同基线重编（Snort 3.13.2 / LibDAQ 3.0.29 / iperf 3.22，GLIBC≤2.28），未到位按本计划断网验收表降级（仅验收 HTTP）。
