# 第一部分 总体设计

## 1. 背景与目标

core-http-bridge 现有能力 = CORE 会话管控平面（会话/节点/链路 CRUD、终端、事件流）。本改造在其上扩展五个 Tab，补齐"靶标交付物 → 节点实例 → 拓扑编排 → 运行监测"的管理闭环。

### 与 AgentCyTE 的关系（定稿）

AgentCyTE = 随机生成拓扑（想定驱动）。Tab4 拓扑管理 = 基于 **bridge 原有拓扑画布扩展**（非自研编排、非 AgentCyTE 封装）：拖拽编排基于已导入的节点实例，导入导出用 **CORE 原生会话格式**（复用 bridge 已有 `POST /api/topology` / SaveXml/OpenXml gRPC）。两条入口并存：想定随机生成（AgentCyTE）/ 手工拖拽编排（Tab4）。

### 四方职责边界

| 层 | 决定权 | 类比 |
|:--|:--|:--|
| **构建平台/配方库** | 有什么服务可声明（服务注册 + 与镜像绑定） | 弹药库 |
| **镜像管理模块** | 交付物的进出、登记、启停、删除 | 军械管理员 |
| **想定** | 声明该节点启动哪些服务 | 作战命令 |
| **CORE** | 按声明执行（投递/启动/校验/停止） | 发射装置 |

### 明确不做的事（职责外）

- ❌ 不探测/不判定镜像"是否真的有漏洞"（演练过程回答，平台不做自动漏洞验证）
- ❌ 不提供运行时模式切换（想定声明即冻结；改模式 = 停止销毁 → 改想定 → 重部署）
- ❌ 不强制 bundle 整包原子导入（三件独立、允许缺件、手动补录——支持外源镜像）
- ❌ 不限制镜像来源（打包导入/外源导入均可，来源仅作登记）

**前端载体**：bridge 现有静态单页控制台（index.html）扩展 —— 现有页面加左侧五 Tab 导航，五视图为同一单页内的前端路由切换（无多页面跳转）；Tab4 拓扑画布复用现有 canvas-area，Tab5 监测复用现有 SSE 基础设施。不引入前端框架依赖（延续原生 HTML/JS 技术栈）。

### 2.2 数据流（三层职责链）

```
Tab1 注册服务定义 → daemon 全局服务池（CORE"认识"服务名）
Tab3 绑定服务到节点实例 → 实例=模板（名字+运行时类型+镜像+服务声明）
Tab4 拓扑引用实例 → 编排连线 → 启动 → CORE 按 node.services 实例化
```

### 2.3 数据模型（平台库）

```
targets（节点实例表，Tab3 的管理对象）
├── name(唯一), runtime_type (docker | netns)
├── image_tag（仅 docker 型；netns 型共享宿主 rootfs）
├── services: [{name, group, mode}]               # 绑定的服务声明（含分组标识）
│     group ∈ {system(基础服务), drill(演练服务)}
│     system 组：sshd/syslog/cron 等基础服务，默认声明（环境可用性）
│     drill 组：httpd-vuln/redis-unauth 等演练目标，按想定声明（模式选择）
├── ports, cve, flags 可选
├── locked: bool                                 # 被拓扑引用时锁定，不可改（可复制）
topologies（拓扑表，Tab4 的管理对象）
├── name, session_id(运行时), status(draft|running|stopped)
├── nodes: [{instance_id, x, y}]               # 引用实例 + 画布坐标
├── links: [{a, b, params}]
images（镜像登记表，Tab1 的管理对象）
├── name:tag, size, imported_at, source(packaged|external)
├── manifest: JSON（软件/CVE/端口/锚点/flags 可选）
├── services_supported: [str]                    # 该镜像可支撑的服务对
    ├── normalized: WORKDIR / + iproute2            # 靶标基座镜像规范化铁律
audit_log（全 Tab 变更审计）
```

### 2.3.1 服务分组（system 基础服务 / drill 演练服务）

| 分组 | 前缀 | 例子 | 默认声明 | 语义 |
|:--|:--|:--|:--|:--|
| `system` | svc-system- | sshd / syslog / cron | ✅ 默认声明 | 环境可用性保障 |
| `drill` | svc-<软件>-<CVE>- | svc-drill-httpd-41773-vuln | 按想定声明 | 红方攻击目标 |

**规则**：
- 基础服务默认声明（环境可用），想定可关闭（如关 sshd 增大攻击难度）
- 演练服务显式声明（vuln/normal 由想定决定），同软件互斥
- UI 按两组分开展示；同组内同软件互斥校验

### 2.4 状态机

```
实例（targets）：未绑定 → 已绑定 → [被拓扑引用: locked] → 解绑 → 可改/删
独立容器（Tab2）：创建 → 运行 → 停止 → 删除
CORE 拓扑会话：部署 → RUNTIME（冻结）→ 停止销毁
模式：部署前按 tag/想定确定 → 运行中冻结 → 停止后可改想定重部署
```

### 靶标包（Target Bundle）—— 交付物单元

```
<靶标名>-bundle/
├── image.tar                # 基座镜像（docker save：软件+配置装好，不自启）
├── manifest.json            # 配方清单（权威绑定：软件/CVE/服务/端口/锚点/flags 可选）
└── services/
    ├── svc-httpd-41773-vuln/
    │   ├── service.py                   # CORE 服务定义类
    │   └── templates/httpd-41773-vuln.sh  # 启动脚本模板（Mako）
    └── svc-httpd-41773-normal/
        ├── service.py
        └── templates/httpd-41773-normal.sh
```

### manifest（配方清单）Schema

```json
{
  "name": "dmz-es1427",
  "software": "elasticsearch",
  "version": "1.4.2",
  "cve": ["CVE-2015-1427"],
  "image": { "name": "target-dmz-es1427", "tag": "v1", "ports": [9200] },
  "services": [
    { "name": "svc-es1427-vuln",   "mode": "vuln",   "startup": "bash /opt/scripts/start.sh", "depends": ["elasticsearch"] },
    { "name": "svc-es1427-normal", "mode": "normal", "startup": "bash /opt/scripts/start.sh", "depends": ["elasticsearch"] }
  ],
  "flags": [ { "name": "flag1.txt", "path": "/flag1.txt", "requires_root": true, "score": 1 } ],
  "anchor": { "vuln": "curl -s http://127.0.0.1:9200/_search -d '...'", "expect": "flag 可达" },
  "notes": "人工编目时填写的备注"
}
```

### 服务命名规范（正式）

```
服务名 = svc-<软件>-<CVE或能力>-<模式>
  模式 ∈ {vuln, normal}      成对注册、同软件互斥、缺省 normal（安全默认）
group = drill/<网段位置>/<漏洞类别>        （分类展示用，非约束）
实例: svc-redis-unauth-vuln / svc-httpd-41773-normal     （命名规范的两个在库实例）
```

### 数据模型（平台库）

```
targets（靶标/实例表，混合拓扑：docker 与 netns 两类节点实例）
├── name, runtime_type (docker | netns)                       # 运行时类型（CORE 原生混合拓扑，实测已验证）
├── image_tag（仅 docker 型有；netns 型共享宿主 rootfs，无镜像）
├── import_source(packaged|external)
├── pieces: { image: bool, services: bool, manifest: bool }   # 三件各自到位状态（netns 型无镜像件）
├── services: [{name, mode}]                                  # 绑定的服务清单（权威绑定；netns 型服务经 vcmd 天然可用）
├── manifest: JSON                                            # 同步自导入/手动编辑
├── ports: [int], cve: [str], flags: [JSON]
├── verify_status: unverified|verified                        # 兼容字段(人工验证结论, 非门禁)
├── created_by/at, updated_at
services（服务注册表）
├── name(全局唯一), mode, software, cve, ports
├── definition_file(源文件路径), bound_targets[]
manifest_versions（清单历史, 可选）
```

## 4. Tab2 容器管理 ✅ 已实现（2026-11-13）

> 实现记录：`static/containers.html`（列表/新建/启停/删除/exec 命令框）+ `static/cterm.html`（WS 终端，复用 term.html ANSI 解码）。后端 `@router.websocket("/ws/containers/standalone/{name}/terminal")`：docker exec -it 挂 pty.openpty() slave（同 vcmd 终端套路），断开 killpg SIGKILL 整组回收无孤儿。§4.2 命名隔离已硬落地：全部接口前置校验 standalone-* 前缀，CORE 拓扑容器 403；§4.4 审计已验证（AUDIT 日志）。

### 职责与边界

管理**独立容器**（非 CORE 拓扑内）——用途：镜像验证、单机工具箱、临时实验。**不管理 CORE 拓扑内容器**（那些随会话生命周期，Tab2 物理不可见）。

### 4.2 命名隔离（硬规则）

| 容器类别 | 命名规范 | 谁能操作 |
|:--|:--|:--|
| 独立容器 | `standalone-<镜像名>-<随机>` | Tab2 页面 |
| CORE 拓扑容器 | `core-<会话id>-<节点名>` | 仅随会话生命周期 |

**Tab2 物理上看不到 CORE 拓扑容器**（按命名前缀过滤），防止误删正在运行的演练。

### 4.3 接口

| 方法 | 路径 | 作用 |
|:--|:--|:--|
| POST | `/containers/run` | 独立启动（镜像+可选端口映射） |
| POST | `/containers/{name}/stop` | 停止 |
| DELETE | `/containers/{name}` | 删除（仅独立容器） |
| GET | `/containers` | 列表（仅 standalone- 前缀） |
| WS | `/containers/{name}/terminal` | 进入终端 |

### 4.4 审计

启动/停止/删除/exec 全留痕（who/when/container/cmd），独立容器的生命周期与审计独立于 CORE 会话。

### 5.1 节点实例模型

```
节点实例 = {
  name(唯一), runtime_type (docker | netns),
  image_tag(仅 docker 型),            # netns 型共享宿主 rootfs，无镜像
  services: [{name, mode}],           # 成对互斥（同软件 normal/vuln 只选一），跨软件可组合
  ports, cve, flags 可选,
  locked: bool                        # 被拓扑引用时锁定
}
```

### 5.2 引用式设计（QD 定稿）

- 实例 = **模板**：拓扑内的节点绑定实例 ID（引用），不复制数据
- 改实例 = 所有引用它的拓扑定义随之更新（下次部署生效）
- **被引用锁定**：locked=true 时禁止修改/删除，UI 提示"已被拓扑 X、Y 引用"
- 出路两条：① 先在拓扑中解除引用再改；② **复制实例为新实例**再改（模板演化常规姿势）

### 5.3 互斥校验（QC/QA 落地）

同节点实例的服务声明中：同软件的 normal/vuln 对**互斥**（二选一）；不同软件可组合（`SshVuln + WebNormal` = 多面手主机）。校验器在保存实例时执行，冲突即拒并指明冲突对。

## 7. Tab5 数据监测 ✅ 已实现（2026-11-14）

> 实现记录：`static/monitor.html` + `/monitor/host`、`/monitor/containers` 端点。§7.1 范围逐项落地：
> **宿主载荷**：/proc 直读（CPU ticks 前端两次采样差分算 %、loadavg、内存、/ 与 /opt 磁盘），3s 轮询
> **CORE 会话内节点**：三分组表深监测（docker stats）+ SSE 三流透传（页面内 EventSource 直连 bridge 既有流）
> **独立容器 / 非 platform 容器**：分组列表可见、不深监测（按命名前缀 + CORE 会话节点名动态归组；DockerNode 容器名=节点名）。**容器生命周期实测（2026-11-14）**：正常 stop 会话即执行 DockerNode shutdown（docker rm -f），容器对象直接销毁——core 组条目随会话停止消失；"其他"组只收留**异常路径孤儿**（core-daemon 被强杀/宿主重启导致会话未走正常 shutdown，如历史演练残留的 Exited (255) 容器），供人工发现与清理。
> **动作监测增强（2026-11-14 定稿）**：
> ① **Events 流持续化 + 详情**（原实现收到首个事件即断且只有类型名）——会话全生命周期持续推送拓扑层动作并序列化详情（node 增删改含节点 id/名字、link 增删含两端节点、alert 告警含级别/来源/文本、session 状态事件），监测页新增「会话动作时间线」窗口。实测：订阅后加节点/连线，实时收到 `{"type":"node","action":"add","node":{...}}` 等详情
> ② **CORE 节点终端命令留痕**——vcmd 终端 WS 后端行缓冲输入，回车落 audit.jsonl（`term.node`，含 session_id/node_id/节点名/输入行），审计页可按动作筛选。实测：终端敲 `echo audit-mark-777` → `{"action":"term.node","node":"audit-node","input":"echo audit-mark-777"}`
> **独立容器完全排除在监测外（含终端命令留痕，用户定稿 2026-11-14）**——与 §7.1"生命周期独立，仅列表可见"一致，容器终端不做命令记录
> **修复的既有 bug（SSE 三流全部数据不通）**：app.py 三个流端点各自定义了 handler 却从未传入——bridge.events/throughputs/cpu_usage 内部注册的是 `lambda e: None`，数据永远到不了响应。已改 bridge.py 三个方法加 handler 参数并接线；throughputs 载荷结构化（ifaces/bridges 明细）；cpu 流补 1s 心跳（原实现循环里压根没有 yield，daemon 不发事件时零字节）、events 流补 5s 心跳。
> **坑**：wrappers.SessionState/NodeType 是普通 Enum（与 int 比较恒 False，统一取 .value）；Session.nodes 是 `{node_id: Node}` 字典不是列表。
> **数据留存（2026-11-15 定稿落地）：SQLite（platform.db）+ drill_id 演练身份**
> 动机：CORE 会话号可回收（stop→restart 同号/删除后计数器只增/**daemon 重启归零重发**——实测确认），裸 session_id 当数据主键会让两场演练混桶。解法：平台签发 `drill_id`（d-日期-短随机，全局唯一）为数据主键，CORE 会话号降级为展示属性。
> 表：`drills`（身份登记：创建签发 active / DELETE closed / reconciler 发现会话消失 interrupted；同号新会话开新行）、`audit`（平台操作+节点终端命令，session_id/node_id/target 成列任意组合过滤）、`events`（拓扑层动作时间线持久化，创建会话即同步订阅——不等 5s tick，头几秒动作不漏录）、`metrics`（RUNTIME 期间 5s 一拍采样 docker 型节点）。
> 约束：标准库 sqlite3 零新依赖（离线部署硬约束）、单写者 WAL、库文件 `/opt/artifacts/core-drill/platform.db`（持久目录）；audit.jsonl 双写保留一个版本期。
> 查询端点：`/drills`、`/audit?action&session_id&node_id`、`/metrics?drill_id&node_id`、`/events?drill_id`。前端：监测页 core 组加「所属演练」列 + 历史指标查询区；审计页加会话筛选。
> 实测 8/8：drill 签发/事件落库/指标采样/终端审计按会话过滤/stop→restart 同 drill 数据连续/归属标注/delete closed/JSONL 双写。
> **运维收尾（2026-11-15，B 包 6/6 PASS）**：① DELETE 会话保护（RUNTIME 中先补 stop+轮询退出再删，修"stop 异步收尾期间立即 delete 失败"）② 保留策略（metrics 30 天/events 90 天/audit 永久；采样线程每小时自动清 + `DELETE /drills/{id}/data` 手动清）③ **core-bridge.service systemd 单元**（enable+active，随 core-daemon 自启，宿主重启不再需要手动拉起）④ logrotate（bridge.log+audit.jsonl weekly×8 copytruncate）。

## 8. 安全与审计

> **演练效果评定类功能裁撤说明（2026-11-15 定稿）**：本平台定位首先是**网络仿真平台**。曾提议的"锚点结果结构化记录 + A/B 防御有效性报告"（A2）已裁撤——漏洞是否可利用、防御是否有效，由演练过程与参演人员自行回答，平台不记录、不评定、不生成报告。环境就绪类检查（A1 预检：容器存活/服务进程/端口可达与声明一致性）不在此列，属仿真平台的正常职责。
>
> **A1 就绪度预检已实现（2026-11-15，4 场景实测通过）**：`POST /precheck?session_id=N`。原则=一切检查项来自"声明"，平台不窥探镜像内容：
> L1 容器存活（DockerNode 容器名=节点名）/ L2 声明服务的 validate 命令（ServiceManager 统一加载内置+custom，经 node_command 在节点内执行）/ L3 编目端口探测（manifest.ports 兼容 image.ports 与顶层两种写法——首版踩过只读顶层的坑）。
> 外源镜像自动降级：声明了服务→L1+L2 照跑（validate 来自服务定义与镜像来源无关）；裸镜像→仅 L1+如实标注"未编目，仅完成存活检查"。
> 判定边界：只回答"环境与声明一致吗"（服务起了没/端口开了没），不回答"漏洞可利用吗"。
> 实测：编目就绪 READY（pidof ok + 80/open）；redis 错配（dmz-base 声明 redis）→ pidof redis-server missing + 端口 closed → NOT_READY（此类错配开打前 30 秒暴露）；外源裸节点降级+标注；netns 节点经 vcmd 校验、CORE 内置 SSH 无 validate 字段→ 如实标 no-validate。
> 前端：画布工具条「🩺 预检」按钮（RUNTIME 态可用，updateFreezeUi 反向控制），结果弹窗按节点列表 + READY/NOT_READY 横幅。预检动作入 audit。

> 审计落地记录（2026-11-14）：`_audit()` 双写——bridge.log（文本）+ `/opt/artifacts/core-drill/audit.jsonl`（结构化），`GET /audit` 可按 action 过滤/limit 查询，页面 `static/audit.html`（动作下拉筛选 + 成功/失败标记）。已留痕动作：image.import/delete、services.import、manifest.save/edit、container.run/stop/start/delete/exec、instance.create/update/delete/clone。
>
> **RBAC 角色模型已裁撤（2026-11-14 定稿）**：平台定位为内网演练环境，访问控制依赖网络边界（内网隔离 + 端口准入），不引入登录/角色体系。全部操作者默认同权限，操作合法性由审计留痕事后追溯。

## 12. 已知 CORE 缺口与规避（实测教训汇总，靶标工厂设计约束）
