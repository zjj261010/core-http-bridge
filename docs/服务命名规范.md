# 服务命名规范（设计稿）

> 版本 V1.0 · 2026-11-24 · 面向镜像包作者/平台维护者
> 目标：**最终服务名"一眼看懂"——谁提供的、什么软件、什么用途、什么模式**，同时兼容平台两项既有机制（导入自动改名、版本固化别名），零代码改动。

---

## 1. 机制约束（不可改，命名规范在此框架内设计）

服务最终注册名由平台两层拼接，命名规范无法绕过，只能利用：

```
最终名 = svc-{清单名}-{服务定义 name}
          ↑ 清单名 = bundle 目录名/manifest.name（包作者定）
          ↑ name   = service.py 类的 name 字段 / catalog 表单（包作者定）
版本别名 = svc-{12hex}-v{n}-{服务定义 name 去掉前缀}     （平台自动生成，发布时固化）
```

- 字符集：最终名限 `[a-zA-Z0-9_-]`；建议全程小写（platform 存量混用，新规范统一小写）
- 清单名（包名）另限 `[a-zA-Z0-9_-]+` 且为 bundle 目录名
- 版本别名是内部形态，**不影响规范设计**（对外/对 UI 展示以最终名为准）

## 2. 命名文法

### 2.1 包名（清单名 = bundle 目录名）

```
package = domain "-" subject
  domain ∈ { vuln      漏洞靶标包（以利用为主）
           , infra     基础设施/服务包（网络角色与公共服务）
           , osvc      原生服务平移包（osvc 系列既有约定，沿用）
           , ext       外源镜像包
           , test      验证/教学包 }
  subject = 主体名（软件名/场景名，[a-z0-9-]+，不含 domain 词）
```

示例：`vuln-httpd-41773`、`osvc-router`、`osvc-server`、`ext-nginx`、`test-web-tiny`

> 兼容注：存量包名（drill、csle-*、guide-verify 等）不强制迁移；新包按本规范。

### 2.2 服务定义 name（service.py 的 `name` 字段 / catalog 服务名）

```
name = software "-" capability [ "-" variant ]
  software   = 提供该能力的软件/协议名（pidof 校验的对象名优先）
  capability = 能力/要点（cgi、heartbleed、ospf、unauth、forward……）
  variant    = 可选：normal / vuln（仅双模式包使用）；单模式包省略
```

- 长度：整段 ≤ 40 字符
- 禁止：`svc-` 开头（导入改名会剥前缀）、`imgmode-`/`imgsvc-` 开头（平台保留前缀）、`default`、`native`（平台语义词）

### 2.3 最终名读法

```
最终名 = svc-{package}-{name}
读法   = "【包域·包主体】包里的【软件·能力·模式】"
```

## 3. 双模式与单模式的命名姿势（catalog 模型推荐态）

catalog 模型推荐：**一个服务 + 多个模式**（部署期 `{服务:模式}` 单选天然互斥，§3.4《镜像导入指南》）。

| 包形态 | 服务（name） | 模式（mode.name） | 漏洞标注（§2.4/指南 4.3） |
|:--|:--|:--|:--|
| 双模式漏洞包 | `httpd-cgi` | `normal`（vulnerable=false）/ `vuln`（vulnerable=true, cve=[CVE-2021-41773]） | 随模式自动区分 |
| 单模式漏洞包 | `proftpd-modcopy` | `vuln`（vulnerable=true, cve=[CVE-2015-3306]） | 红标 |
| 基础设施包 | `frr-routing` / `server-ssh` | `run`（vulnerable=null 不适用） | 灰标 |

**最终名对照**（legacy 三件套导入路径下 name 段直接拼入）：

| 包（package） | 服务定义 name | 最终注册名 |
|:--|:--|:--|
| vuln-httpd-41773 | httpd-cgi-normal | `svc-vuln-httpd-41773-httpd-cgi-normal` |
| vuln-httpd-41773 | httpd-cgi-vuln | `svc-vuln-httpd-41773-httpd-cgi-vuln` |
| osvc-router | frr-routing | `svc-osvc-router-frr-routing` |
| infra-server | server-ssh | `svc-infra-server-server-ssh` |

> 长度提示：legacy 双层拼接会产生「包名+name」重复语义段（如 httpd 出现两次）。控制口诀：**包名带场景，name 带软件与要点，模式段只出现一次**。仍超长时可精简 name 的软件段（包名已含软件信息时 name 允许省略软件段，如 osvc 系的 `osvc-http` 直接读作"包 osvc-server 的 http 服务"）。

## 4. 语义段细则

### 4.1 capability（能力/要点段）词汇表（开放扩展，示例为已用词）

| 词 | 语义 |
|:--|:--|
| cgi | CGI 执行面（httpd） |
| heartbleed | TLS 心跳泄漏 |
| modcopy | FTP 任意复制 |
| sender | mail 参数注入 |
| groovy | 动态脚本执行 |
| unauth | 未授权访问 |
| forward / nat | 转发 / 地址伪装 |
| routing | 路由协议族 |
| ssh / http / ftp / dhcp / dns | 明文服务名 |

### 4.2 variant（模式段）

- 仅双模式包使用：`normal`（无洞基线）/ `vuln`（有洞）
- 单模式漏洞包：**省略 variant**，漏洞语义由漏洞标注字段（vulnerable=true + cve）表达——**推荐**，避免名字与标注双轨
- 基础设施服务：省略 variant

---

## 5. 命名禁则

| 禁则 | 原因 |
|:--|:--|
| 禁 `svc-`/`imgmode-`/`imgsvc-` 作 name 开头 | 导入改名剥前缀/平台保留前缀，语义错乱 |
| 禁与同包内其他服务同名（导入 409） | 平台唯一性校验 |
| 禁跨包抄袭他包服务名（不同包可用同名 name，导入会自动带各自包前缀不冲突；但**禁止**故意构造与他包最终名完全相同的 name 规避归属） | 包自治（P4） |
| 禁大写字母、下划线、空格、点 | 字符集统一 [a-z0-9-] |
| 禁测试名混入生产包（`test`/`tmp`/`demo` 仅限 test 域包） | 域语义纯净（坑：guide-verify 测试包混入生产清单已演示过清理成本） |

## 7. 与平台机制的对照确认

| 机制 | 本规范的关系 |
|:--|:--|
| 导入改名 `svc-{清单名}-{原名}` | 规范只设计清单名与 name 两段输入，拼接机制不变 |
| 版本别名 `svc-{12hex}-v{n}-…` | 平台自动生成，规范不涉及（对外展示以最终名为准） |
| 漏洞标注 vulnerable/cve | 与 name 的 variant 段**解耦**：标注是元数据可随时改；name 是注册名改则新修订——推荐漏洞语义以标注为准，name 中 variant 段仅双模式包惯例使用 |
| 动作映射字典（只读） | 字典编码（exploit_id/action 编码）独立于服务命名，不冲突 |
| catalogs 只读化（9fd9662） | 不影响命名（命名在 bundle/清单编辑层） |

## 8. 快速判定（给人用的速查）

拿到一个最终名，从左到右读：

```
svc-                          → 平台自定义服务
  {包域}-{主体}                → 谁提供的、什么场景
    {name 段…}                 → 什么软件、什么能力
      [-normal|-vuln]          → （若有）无洞基线 / 有洞
      （无 variant 段）          → 单模式包，漏洞语义看标注列
```

例：`svc-vuln-proftpd-3306-proftpd-modcopy`
= vuln 域 / proftpd-3306 包 / proftpd 的 modcopy 能力（漏洞态由标注列确认）。
