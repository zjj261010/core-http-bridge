# 数字平台对接接口文档

> 版本：V1.0（2026-11-24，随 core-http-bridge b5438da 实现态编写）
> 读者：数字平台（智能训练＋推演评估系统）开发与联调人员。
> 定位：本文档是**容器平台（CORE ＋ core-http-bridge）作为提供方**的对接规格——覆盖攻击动作序列下发（IF-01）、执行结果回传（IF-02）、Snort 告警回传（IF-03）三接口的**已实现**行为。设计语义见《数字平台与容器平台交互设计 V1.0》与《开发说明书 V1.1》；一般外部调用契约见《接口文档-外部调用版.md》。
> 一期实现边界：可执行动作仅 `HttpServiceCheck`（预置 HTTP 服务检查）。红方动作空间全量映射（ExploitRemoteService 等）为独立需求，未实装——字典条目已预留扩展位（§7）。

## 1. 对接前置条件（容器平台侧配置）

| 配置项 | 环境变量 | 说明 |
|:--|:--|:--|
| 入向鉴权 | `BRIDGE_VALIDATION_TOKEN` | 必配。未配置时 IF-01 整体未启用（任何请求返回 503/1501）。数字平台调用须携带 `Authorization: Bearer <token>` |
| 出向回调地址 | `BRIDGE_VALIDATION_CALLBACK_URL` | 必配。数字平台接收端的 base URL（仅接受 http/https、根路径，如 `https://digital.example.com`）；IF-02/03 由容器平台按此地址主动推送 |
| 出向回调鉴权 | `BRIDGE_VALIDATION_CALLBACK_TOKEN` | 可选。配置后容器平台回传请求携带 `Authorization: Bearer <token>`，数字平台接收端校验 |

以上均为容器平台 core-bridge 服务的进程环境变量（systemd `Environment=` 或 drop-in 配置），变更后 `systemctl restart core-bridge` 生效。

**拓扑侧前置要求**（部署时固化，任务受理前置校验项）：

| 标记 | 节点属性 | 约束 |
|:--|:--|:--|
| 序列执行节点 | `validation_source = true` | 每拓扑至多一个；须为本机 CORE 原生节点或 Docker 节点；所有动作由该节点发起 |
| HTTP 验证目标 | `validation_http_port`（1–65535） | 每拓扑至多一个；目标节点声明此端口表示"该端口上有可验证的 HTTP 服务" |

标记方式：容器平台拓扑编辑页节点属性勾选/填写（`validation_source` / `validation_http_port` 字段），保存进拓扑修订、部署时固化到运行快照。旧拓扑无标记仍可正常运行，但要受理验证任务必须部署带标记的修订。

**联调工具**：容器平台自带回环 Mock 接收端 `scripts/mock-validation-receiver.py`（记录收到的 IF-02/03 报文、可模拟确认丢失），联调初期 `BRIDGE_VALIDATION_CALLBACK_URL` 可先指向它。

## 2. IF-01 攻击动作序列下发

```
POST /api/v1/attack-sequences
Content-Type: application/json; charset=utf-8
Authorization: Bearer <BRIDGE_VALIDATION_TOKEN>
```

### 2.1 请求报文

```json
{
  "scenario_id": "41",
  "sequence_id": "demo-001",
  "actions": [
    {
      "seq": 1,
      "action_name": "HttpServiceCheck",
      "target_node": { "subnet": "lab", "ip": "10.99.0.1" },
      "params": { "check_id": "web-health" }
    }
  ]
}
```

### 2.2 字段规格

| 字段 | 类型/约束 | 说明 |
|:--|:--|:--|
| `scenario_id` | 十进制正整数字符串 | **即容器平台当前运行中的 CORE session_id**。数字平台经会话查询接口取得运行会话后原样传入；容器平台校验其处于运行态 |
| `sequence_id` | 非空字符串 ≤128 | 每次新任务全新生成（建议 UUID）。幂等键 = (scenario_id, sequence_id)：同键同文返回原回执；同键异文 409/1005 |
| `actions[]` | 1–64 步 | 按 seq 排序后必须为 1…N 连续，重复/缺号拒绝（1004） |
| `actions[].seq` | int ≥1 | 执行顺序 |
| `actions[].action_name` | ≤64 字符 | 必须在动作字典目录内（当前可执行：`HttpServiceCheck`）；未知动作 1002 |
| `actions[].source_node` | 可省略 | 省略时使用部署标记的序列执行节点；提供时与标记节点接口核对（subnet/ip 须匹配），不匹配报 1003 |
| `actions[].target_node` | 必填 `{subnet, ip, hostname?}` | 必须对应本次部署标记的 HTTP 验证目标（subnet/ip 核对）；IP 为合法 IPv4 字面量 |
| `actions[].params.check_id` | 默认 `web-health` | 当前仅接受 `web-health`（场景预设检查项） |

### 2.3 受理响应

```json
HTTP 200
{ "code": 0, "message": "accepted", "scenario_id": "41", "sequence_id": "demo-001",
  "dictionary_version": "validation/2" }
```

- `code=0` 表示已受理并完成预校验（此时**尚未执行**——实际 HTTP 可用性在步骤内判定）。
- `dictionary_version` 受理时钉定的字典版本，随 IF-02 原样回传。

### 2.4 错误码（IF-01）

| code | HTTP | 触发条件 | 数字平台处理 |
|:--|:--:|:--|:--|
| 1000 | 401 | 调用凭据无效（缺/错 Bearer Token） | 检查双方凭据配置 |
| 1001 | 409 | 会话不存在/未运行；或会话运行实例已变化（重启/复用） | 中止本次实测，确认会话后重发新 sequence_id |
| 1002 | 400 | 动作名不在字典目录内 | 中止并告警，核对字典版本 |
| 1004 | 400 | 请求格式无效（pydantic 校验：缺字段/类型错/seq 不连续/超出上限） | 修正报文 |
| 1005 | 409 | 相同幂等键但报文内容不同 | 冲突：核对 sequence_id 是否复用 |
| 1006 | 409 | 该会话已有未完成的验证序列 | 等待当前任务完成（可轮询查询端点） |
| 1501 | 503 | 验证接口未启用 / CORE 会话状态暂不可确认 | 容器平台侧配置或 CORE 状态问题，联系运维 |

注意校验顺序：请求格式校验（1004）先于鉴权（1000）执行——格式非法的报文即使 Token 正确也返回 400/1004。

## 3. 任务执行语义（容器平台内部行为，供数字平台理解回传数据）

受理后容器平台按以下语义自动执行，数字平台无需再下发任何指令：

1. **执行节点**：全部动作在部署时标记的 `validation_source` 节点内执行（nsenter 进入其网络命名空间）；源节点 IP 即该节点在拓扑中的接口地址。
2. **逐步记录**：每步记录 started/ended（UTC RFC3339 毫秒）、duration_sec（单调时钟）、exit_code、reason。
3. **失败即停**：某步 FAIL 后后续步骤记 SKIPPED（reason 注明前序失败）。
4. **观测窗口**：任务受理时记录 Snort 探针基线与事件游标；执行窗口 = 第一步开始至最后一步结束＋收集宽限期（2s）。窗口内、命中部署内 Snort 探针、且源/目的五元组可唯一归属某步的告警，标记 `seq` 归属该步；无法唯一归属的告警 `seq=null` 保留在窗口观测中。
5. **观测状态**：`complete`（探针覆盖整个窗口）/ `partial`（有缺口或丢包）/ `unavailable`（无运行探针）。探针部署见《接口文档-外部调用版.md》§3.4 network_activity 声明。
6. **会话异常**：会话停止/被替换/容器平台中断时，任务立即封存——已完成步骤保留事实，中断且无法确定结果的记 FAIL（reason=interrupted_outcome_unknown），随后照常回传。
7. **结果不可变**：冻结后的结果不随重试重新生成；重发仅重放已冻结报文。

一期动作的判定基准：`HttpServiceCheck` 对目标 `<ip>:<port>` 发起受限 HTTP GET——HTTP 2xx 且退出码 0 → SUCCESS；连接失败/超时 → FAIL（reason=http_check_failed / http_check_timeout）。

## 4. IF-02 实际执行结果序列上传（容器平台 → 数字平台）

```
POST /api/v1/execution-results
Authorization: Bearer <回调 Token（若配置）>
```

```json
{
  "scenario_id": "41",
  "sequence_id": "demo-001",
  "dictionary_version": "validation/2",
  "results": [
    { "seq": 1, "action_name": "HttpServiceCheck", "actual": "SUCCESS",
      "exit_code": 0, "reason": null,
      "started_at": "2026-11-24T06:30:00.000Z", "ended_at": "2026-11-24T06:30:00.420Z",
      "duration_sec": 0.42, "source_node_id": 3, "target_node_id": 7,
      "stdout_digest": "HTTP 200" }
  ]
}
```

### 字段说明

| 字段 | 说明 |
|:--|:--|
| `dictionary_version` | 受理时钉定的字典版本，原样回传 |
| `results[].actual` | `SUCCESS`（完成且符合判据）/ `FAIL`（已尝试失败）/ `SKIPPED`（前序失败被跳过） |
| `results[].exit_code` | 有真实退出码传整数；未启动或未知传 `null` |
| `results[].reason` | 跳过/失败原因：`http_check_failed` / `http_check_timeout` / `node_or_interface_unavailable` / `interrupted_outcome_unknown` / 前序失败说明；成功为 `null` |
| `results[].started_at / ended_at` | UTC RFC3339 毫秒；未执行传 `null`；duration_sec 未执行传 0 |
| `results[].source_node_id / target_node_id` | 实际绑定的容器平台节点编号 |
| `results[].stdout_digest` | 输出摘要（如 `HTTP 200`），UTF-8 ≤2KiB 字符边界截断，可选 |

### 数字平台接收端要求

- 成功确认 = HTTP 2xx ＋ `code=0` ＋ `received_steps` 与整包步骤数一致
- 收到相同结果的重试（幂等重放）应返回同样的确认
- 按 (scenario_id, sequence_id) 关联受理时下发的期望序列，逐步对齐入库（action_records）

## 5. IF-03 Snort 告警上传（容器平台 → 数字平台）

```
POST /api/v1/snort-alerts
```

IF-02 确认后开始发送；每批 ≤100 条；批号 `batch_no` 从 1 连续递增；**同一序列只允许一个尾批（is_last=true），空告警也发空尾批**。

```json
{
  "scenario_id": "41",
  "sequence_id": "demo-001",
  "batch_no": 1,
  "is_last": true,
  "observation_status": "complete",
  "alerts": [
    { "event_id": "run-xxx:815", "probe_id": "probe-1", "seq": 1,
      "ts": "2026-11-24T06:30:05.200Z", "sid": "1:1000001", "priority": 3,
      "src_ip": "10.99.0.10", "src_port": 40211, "dst_ip": "10.99.0.1", "dst_port": 8080,
      "proto": "TCP", "msg": "Bridge IDS verification" }
  ]
}
```

| 字段 | 说明 |
|:--|:--|
| `observation_status` | `complete` / `partial` / `unavailable`（跟随批次，空数组也带状态） |
| `alerts[].event_id` | 事件稳定标识（`<run_id>:<事件id>`），接收端去重键（三元组 场景/序列/批号 + event_id） |
| `alerts[].seq` | 可唯一归属某步时为该步 seq；否则 `null`（背景流量重叠等场景） |
| `alerts[].ts` | UTC RFC3339 毫秒，**抓包时间**（非入库时间） |
| `alerts[].sid` | 规则标识 `GID:SID` 字符串；`priority` 规则优先级；历史源数据缺失可空 |

每批确认 = HTTP 2xx ＋ `received_alerts` 等于该批长度（含重复接收）。

## 7. 动作字典与漏洞标注对接（扩展预告）

当前可执行动作仅 `HttpServiceCheck`。动作映射表真实化后，`ExploitRemoteService` 等动作将按 `params.exploit_id` 映射到具体利用方式——**exploit_id 与靶标漏洞标注（`service_pairs[].cve`）的双向索引**如下（靶标库已实测素材，登记格式与《action-dictionary-drafts.json》一致）：

| exploit_id | 靶标镜像 | CVE | 命令模板要点 | 成功判据 |
|:--|:--|:--|:--|:--|
| shellshock_cgi | target-csle-shellshock:v1 | CVE-2014-6271 | curl UA 注入 `/cgi-bin/vulnerable` | 目标 /tmp 标记文件存在（注入命令须绝对路径） |
| heartbleed_ssl | target-csle-heartbleed:v1 | CVE-2014-0160 | nmap --script ssl-heartbleed | 输出 VULNERABLE |
| sqli_login_bypass | target-csle-sqli:v1 | — | curl POST `' OR '1'='1' --` | 响应含全部用户行/FLAG |
| proftpd_mod_copy | target-csle-proftpd-3306:v1 | CVE-2015-3306 | SITE CPFR/CPTO + curl | webshell 响应 uid=33 |
| phpmailer_10033 | target-csle-phpmailer-10033:v1 | CVE-2016-10033 | exploit.sh multipart POST | backdoor.php 响应 uid=33 |
| es_groovy_1427 | target-csle-es1427:v1 | CVE-2015-1427 | _search script_fields Math 绕过 | exec.value 含 uid=0 |
| sudo_14287 | target-csle-sudo-0426:v1 | CVE-2019-14287 | sudo -u#-1 find -exec | uid=0 |

外部系统按 `POST /targets/image/detail` 读取 `service_pairs[].cve`，即可把靶标漏洞清单映射进推演模型；字典真实化后此处格式保持稳定。

## 8. 联调与验收清单（对照 V1.1 §7）

| 编号 | 场景 | 通过条件 |
|:--|:--|:--|
| 01 正常 | 带源标记、目标 HTTP 服务、Snort 探针的运行拓扑下发预置检查 | 真实请求成功产生真实告警；接收端日志 IF-02 先于全部 IF-03 |
| 02 校验与幂等 | 停止会话/不存在节点/缺标记/未知检查项均有明确错误码；并发重发仅一次执行；同键异文拒绝 | 错误码表 §2.4 全覆盖 |
| 03 失败与中断 | 验证服务不可用记 FAIL＋后续 SKIPPED；中断后已完成步骤可查，旧任务不绑定复用同号新会话 | — |
| 04 回传与空批 | IF-02 超时/确认后断线；0/100/101 条告警的尾批、批号、去重、确认数 | — |
| 05 观测归属 | 背景流量并存时不确定归属的告警 seq=null；探针停止与零告警可区分 | — |

容器平台侧已具备：Mock 接收端（`scripts/mock-validation-receiver.py`，支持确认丢失模拟）、定向测试 23 项、隔离库验收。数字平台侧需提供：接收端地址与 Token、样例序列生成器。
