## 2. 装平台（core-http-bridge）

**目标**：服务起来，浏览器能开页面。约 5 分钟。

```bash
cd /opt/drill-offline/bridge-v1.3-8eab1c9

# ① 校验主包（预期：全 OK）
sha256sum -c SHA256SUMS.txt

# ② 安装/升级（旧版会自动备份到 /var/backups/core-http-bridge/，可回滚）
bash install.sh --python /opt/core/venv/bin/python3 --bridge-dir /opt/core-http-bridge

# ③ 起服务并验活
systemctl restart core-bridge
curl -s http://127.0.0.1:8080/health
# 预期：{"status":"ok",...}
```

**三种可能的结果**

| 现象 | 含义 | 怎么办 |
|:--|:--|:--|
| 自检通过，正常走完 | venv 干净 | 无 |
| 提示「自检未过」+ 给出补装命令 | 现场 venv 和清单有版本差（常见：缺 httptools/python-dotenv/uvloop/watchfiles） | 按提示原样执行补装命令，再跑一遍 install.sh |
| venv 损坏 / 全新机器 | — | 加 `--fresh` 参数重跑（用包内 wheels 新建环境，已实测闭环） |

**回滚**（万一要退回旧版）：

```bash
tar xzf /var/backups/core-http-bridge/bridge-<时间戳>.tgz -C /opt/
systemctl restart core-bridge
```

## 3. 确认 CORE 连接（页面报「CORE 未连接」看这里）

`/health` 返回 ok 只说明平台活着；**页面左侧能列出会话**才算 CORE 连通。

```bash
ss -ltn | grep 50051                                # ① 预期：有一行 LISTEN（CORE 的端口）
systemctl status core-daemon --no-pager | head -5   # ② 预期：active (running)
```

- ① 没输出或 ② 不是 active → `systemctl start core-daemon`，然后浏览器刷新。
- 还不行 → `journalctl -u core-bridge --since '10 min ago' --no-pager | tail -20` 看报错。

> 浏览器差异提示：一个浏览器报「未连接」另一个正常，多半是**缓存**——Ctrl+F5 强刷。

## 4. 导入靶标镜像

**目标**：管理页「镜像」里能看到靶标，能拖进拓扑。按演练需要选导（不必 13 个全导）。
`image-imports/` 下现在就是 13 个单文件包（`<包名>.tar.gz`），不再是散件目录。

| 先导这些（跑通全 docker 演练） | 再按需 |
|:--|:--|
| `csle-attacker-kali`（攻击机 1.1G） | `csle-*` ×7 漏洞靶标（shellshock/sqli/proftpd/phpmailer/heartbleed/sudo/es1427） |
| `drill-fw` + `dmz-httpd-41773` + `inn-redis`（防火墙/DMZ/内网） | `osvc-router` / `osvc-server`（原生服务拓扑） |

每个包 = **一个 .tar.gz 文件**（内含镜像+清单+服务定义），两条命令导入：

```bash
B=http://127.0.0.1:8080
PKG=<包名>          # 如 csle-sqli

# ① 上传整包（服务端自动解包；不用填名称——暂存目录自动按包内清单名落位）
DIR=$(curl -s -X POST "$B/targets/import/bundle/upload" \
  --data-binary @/opt/drill-offline/image-imports/$PKG.tar.gz \
  | grep -o '"dir": *"[^"]*"' | cut -d'"' -f4)
echo "解包到: $DIR"

# ② 正式导入（docker load + 服务注册 + 清单编目一次完成）
curl -s -X POST $B/targets/import/bundle -H 'Content-Type: application/json' \
  -d "{\"dir\": \"$DIR\"}"
```

**预期**：① 返回的 `inventory` 三项齐（has_image_tar / py / has_manifest）；② `pieces` 三件都 `"ok": true`（kali 1.1G，load 要等一会）。

**确认生效**（两查）：

```bash
curl -s "$B/targets/manifest/$PKG" | grep -o '"name": *"[^"]*"' | head -2
# 预期：能列出清单（服务名已自动加 svc-<包名>- 前缀）

curl -s $B/instances/available-services | grep -o "svc-$PKG[^\"]*"
# 预期：至少一行（服务可声明）
```

> 管理页「导入」按钮（整包上传）与此等价。「镜像」页的统计口径＝**凡经本项目导入接口导入的镜像**
> （哪怕只导镜像件、暂无清单也计入）；宿主上自行 docker load/pull、没走接口的不统计（2026-11-26 起）。
> 导入/编辑清单的进阶操作见《镜像导入指南》§5——日常按上面命令导完即可用，不用读它。

## 6. 网络工具包（snort 探针 + iperf3 背景流量）

> **什么时候需要它**：演练要出 IDS 告警（Snort 探针）、要起背景流量（iperf3）。
> 建拓扑、打漏洞本身**不需要**。可以最后装、随时装。

### 6.1 这个包的结构（先懂这个，后面就不绕）

包目录里那个 121M 的 `…-bundle.tar.gz` 是**外层箱子**，里面装着：

```
core-network-tools-kylinv10-x86_64-20261125-bundle.tar.gz   ← 外层箱子（解它）
├── core-network-tools-kylinv10-x86_64-20261125.tar.gz       ← ★ 真正要装的载荷
├── SHA256SUMS.txt / VERSIONS.txt                            ← 校验与构建信息
└── evidence/                                               ← 构建方的验证证据（不用动）
```

**真正要装的载荷解开后**是 `/opt/core-network-tools/`，里面三样：

```
/opt/core-network-tools/
├── snort/   ← snort 3.13.2 + 私有 libpcap（自带，不依赖系统）
├── daq/     ← 抓包模块（snort 依赖）
└── iperf/   ← iperf3 3.22（背景流量）
```

它**不需要编译、不需要安装器**——解压到哪里，哪里就是它的家；平台通过环境变量 `CORE_BRIDGE_NETWORK_ROOT` 知道它在哪（默认就是 `/opt/core-network-tools`）。

### 6.2 安装四步

```bash
cd /opt/drill-offline/core-network-tools-kylinv10

# ① 解外层箱子 + 校验
tar xzf core-network-tools-kylinv10-x86_64-20261125-bundle.tar.gz
sha256sum -c SHA256SUMS.txt
# 预期：core-network-tools-…tar.gz: OK

# ② 系统库预检（这 4 个库走麒麟系统自带，工具包不带；缺了才需要补）
ldconfig -p | grep -E 'libcrypto.so.1.1|libssl.so.1.1|libpcre2-8.so.0|libz.so.1|libuuid.so.1'
# 预期：5 行输出（snort/iperf3 都要用 openssl 1.1）。若缺（极少见）：dnf install openssl-libs pcre2 zlib libuuid 后再看

# ③ 解真载荷到 /opt（一步完成"安装"）
tar xzf core-network-tools-kylinv10-x86_64-20261125.tar.gz -C /opt/

# ④ 平台自检（用装平台的那个 python）
/opt/core/venv/bin/python3 /opt/drill-offline/bridge-v1.3-8eab1c9/src/scripts/offline-check.py --network-tools
# 预期最后一行：离线部署自检通过
```

### 6.3 首验（必做一次：证明 snort 在这台真机上真的能抓包出告警）

> 为什么必做：工具是在另一台机器上编译的，"能不能实时抓包出告警"只有真机能证明。
> 方法：造一对虚拟网线（veth），从一端发一个带特征串的请求，看 snort 在另一端能不能嗅到并告警。
> **全程自包含**（不碰真实网卡），跑完即拆。

```bash
ROOT=/opt/core-network-tools

# ① 造测试规则：看到含 BRIDGE_IDS_CHECK 的流量就告警
cat > /tmp/bridge-check.rules <<'EOF'
alert tcp any any -> any any (msg:"Bridge IDS verification"; content:"BRIDGE_IDS_CHECK"; sid:1000001; rev:1;)
EOF

# ② 造一对虚拟网线 + 起一个小 web 服务（在网线另一头）
ip netns add srv
ip link add v0 type veth peer-name v1
ip link set v1 netns srv
ip addr add 10.200.0.1/24 dev v0 && ip link set v0 up
ip netns exec srv sh -c 'ip addr add 10.200.0.2/24 dev v1 && ip link set v1 up'
ip netns exec srv sh -c 'python3 -m http.server 5998 --bind 10.200.0.2 &' sleep 1

# ③ 起 snort 盯住 v0 这头（输出存到 /tmp/snort-stdout）
LD_LIBRARY_PATH=$ROOT/daq/lib $ROOT/snort/bin/snort \
  -c $ROOT/snort/etc/snort/snort.lua -R /tmp/bridge-check.rules \
  --daq-dir $ROOT/daq/lib/daq --daq pcap --daq-mode passive -i v0 -k none \
  -A alert_json --daq-batch-size 1 -l /tmp/snort-log > /tmp/snort-stdout 2>&1 & sleep 3

# ④ 从另一头发一个带特征串的请求
curl -s --noproxy '*' -m 5 "http://10.200.0.2:5998/?probe=BRIDGE_IDS_CHECK" >/dev/null; sleep 2

# ⑤ 判定：snort 的输出里有没有抓到（预期输出 ≥1）
grep -c BRIDGE_IDS_CHECK /tmp/snort-stdout

# ⑥ 收尾：停 snort、拆虚拟网线
pkill -f 'snort.*bridge-check' ; ip netns del srv ; ip link del v0 2>/dev/null
```

> ⚠️ `--daq-batch-size 1` 不能省：安静链路上 pcap 抓包默认攒批，不带这个参数会零告警
> （曾把排查带偏很久，实测定论）。平台生产起探针时也是带这个参数的，测试与生产同形。

### 6.4 首验结果怎么处理

| 结果 | 动作 |
|:--|:--|
| ⑤ 输出 ≥1 | ✅ 通过。什么都不用再做——已装在 `/opt/core-network-tools`，平台默认就用它 |
| ⑤ 输出 0 | 先自查两件事：命令是否原样照抄（尤其 `--daq-batch-size 1` 和 `LD_LIBRARY_PATH`）；`/tmp/snort-stdout` 里 snort 是否起来过（有无报错）。自查后仍 0 → 把 `/tmp/snort-stdout` 全文、`$ROOT/snort/bin/snort -V` 输出、`cat /etc/os-release` 三样收集起来反馈构建方，**先不要用于正式演练** |

### 6.5 验证平台认到了

```bash
curl -s http://127.0.0.1:8080/network-activity/capabilities | grep -o '"iperf3": *[a-z]*\|"snort": *[a-z]*'
# 预期：两项都是 true
```

## 8. 排障速查

| 症状 | 处置 |
|:--|:--|
| 页面「CORE 未连接」 | §3 两查；多为 core-daemon 没起。单个浏览器异常=缓存，Ctrl+F5 |
| 页面下半空白 | 已修复的 CSS 兼容问题（`100dvh` 旧内核不识）。确认页面引用 `workbench.css?v=20261126-1`；仍空白则 Ctrl+F5 + 页面缩放 100% |
| 自检报「缺少工具 ss」 | 已修复（ss 在麒麟位于 /usr/sbin）。旧包现场可升级平台代码；新包已含 |
| install.sh 自检未过 | §2 结果表第二行：按提示补装后重跑，或 `--fresh` |
| kali 包 sha 校验 FAILED | 在 `image-imports/` 目录里跑 `sha256sum -c csle-attacker-kali.tar.gz.sha256`（文件记相对路径）；仍败=part 传输损坏，重传该 part |
| apply 卡 pending | 生效前提是零活跃 CORE 会话：先停止历史会话再重新确认 |
| 页面打不开（curl 000） | `systemctl status core-bridge`、`ss -ltn \| grep 8080`、防火墙放行 8080 |
| snort 报找不到 libdaq.so.3 | 起探针命令要带 `LD_LIBRARY_PATH=$ROOT/daq/lib`（§6.3 原样照抄） |
| `ldd daq_pcap.so` 报 libpcap not found | **假故障**（soname 复用机制），判定只看 §6.3 首验告警数，别管 ldd |
| 删镜像 409 | 有容器/实例引用。先停删演练会话；被想定引用的走「复制出路」 |
| 演练后机器卡 | vcmd 残留进程：`ps -eo pid,cmd \| grep 'vcmd.*pycore'`，`kill -9` 连父进程一起 |
| 杀 uvicorn 自杀 | 别用 `pkill -f`，用 `ps \| awk \| xargs kill` |

## 9. 交付边界（这些"没有"是正常的）

- 网络工具包首验（§6.3）未通过前，不用于正式演练的 IDS 验收
