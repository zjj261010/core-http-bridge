> **版本基线**: ab7c9e5（2026-11-19；上一基线 cf42836 的四大领域行为不变，本次为增补）
> **读者**: 通过 HTTP/JSON 调用 CORE 网络仿真的外部系统（含外部 Vue3 前端）

## 0. 快速上手

四个调用完成"建拓扑 → 启动 → 验证连通 → 清理"。直接可抄：

```bash
B=http://localhost:8080

# ① 导入拓扑（JSON，2 个 netns 节点 + 显式 IP 链路）→ 自动创建会话
curl -s -X POST $B/api/topology -H 'Content-Type: application/json' -d '{
  "name": "demo",
  "nodes": [
    {"id": 1, "name": "r1",  "type": "router", "model": "router", "services": ["zebra", "OSPFv2", "IPForward"]},
    {"id": 2, "name": "pc1", "type": "host",   "model": "PC",     "services": ["DefaultRoute"]}
  ],
  "links": [
    {"node1_id": 1, "node2_id": 2,
     "iface1_ip4": "10.0.0.1", "iface1_ip4_mask": 24,
     "iface2_ip4": "10.0.0.2", "iface2_ip4_mask": 24}
  ]
}'
# → 201  {"session_id":2,"deployment_id":"deploy-bc15263b10c7481288600c7c9e5d41d1","name":"demo","nodes":2,"links":1}
#        注意：只创建不启动，session_id 是后续所有操作的句柄

# ② 启动会话（实例化节点、启动服务）
curl -s -X POST $B/api/sessions/2/start -H 'Content-Type: application/json' -d '{"definition": false}'
# → {"result":true,"exceptions":[]}

# ③ 在节点上执行命令验证连通
curl -s -X POST $B/api/sessions/2/nodes/1/command -H 'Content-Type: application/json' \
     -d '{"command": "ping -c 1 -W 1 10.0.0.2"}'
# → {"return_code":0,"output":"PING 10.0.0.2 ... 1 received, 0% packet loss ..."}

# ④ 删除会话（清理全部仿真资源）
curl -s -X DELETE $B/api/sessions/2
# → {"result":true}
```

## 1. 全局约定

### 1.1 基础

| 项 | 值 |
|:--|:--|
| Base URL | `http://<host>:8080`（直连）或 `http://<host>`（80, nginx 同源反代——**路径完全一致**, SSE/WS 透明转发） |
| 协议 | HTTP/1.1 + WebSocket / SSE（见附录） |
| 认证 | 无（靠内网隔离 + 端口准入，平台设计定稿不设 RBAC） |
| 编码 | UTF-8；请求体 `Content-Type: application/json`（拓扑导入另支持 XML） |
| OpenAPI | `/openapi.json`（机器可读契约, 可生成 TS 类型）＋ Swagger UI `/docs`（自托管资产, 离线可用） |

### 1.2 两套响应信封（并存，按端点区分）

历史原因存在两种风格，**按路径区分**：

| 风格 | 适用路径 | 成功形态 | 失败形态 |
|:--|:--|:--|:--|
| **桥接风格**（老） | `/api/*`（会话/节点/链路/服务/拓扑导入） | HTTP 2xx + 裸业务对象 | 非 2xx + `{"error": "...", "detail": "...", "hint": "..."}`（detail/hint 可缺省） |
| **平台风格**（新） | `/instances*`、`/targets*`、`/containers/*`、`/monitor/*`、`/audit`、`/drills*`、`/metrics`、`/events`、`/precheck`、`/versions/*`、`/storage/*` | `{"ok": true, "data": <业务对象>}` | HTTP 4xx/5xx + `{"ok": false, "error": {"code": "...", "message": "...", ...附加字段}}` |

判定成功的推荐写法（两套通用）：**先看 HTTP 状态码，再按上述形态取值**。

```bash
# 桥接风格失败示例（实测）
curl -s http://localhost:8080/api/sessions/999
# → 404  {"error":"session 999 not found","detail":"gRPC status: NOT_FOUND","hint":"session_id 不存在，请先 POST /api/sessions 创建"}

# 平台风格失败示例
# → 409  {"ok":false,"error":{"code":"INSTANCE_LOCKED","message":"被拓扑引用，禁止删除: d-xxx（会话2）","referenced_by":["d-xxx（会话2）"]}}
```

### 1.3 会话状态枚举（state 字段）

| 值 | 名称 | 含义 |
|:--:|:--|:--|
| 1 | DEFINITION | 定义态：只有拓扑定义，无运行时资源 |
| 2 | CONFIGURATION | 配置中（过渡态） |
| 3 | INSTANTIATION | 实例化中（start 进行时） |
| 4 | RUNTIME | 运行态：节点/服务已启动 |
| 5 | DATACOLLECT | 数据采集态（运行中开启采集） |
| 6 | SHUTDOWN | 关闭中 |

### 1.4 演练身份 drill_id

- **签发**：`POST /api/sessions` 或 `POST /api/topology` 创建会话时自动签发，格式 `d-YYYYMMDD-HHMMSS-<16位hex>`（如 `d-20261117-165736-c4a597b34b97acad`）。
- **为什么需要**：CORE 会话号是"最小未用号"回收策略（删除即复用），不能做数据主键；drill_id 才是稳定标识。
- **identity_status** 字段：`confirmed`（已确认绑定）/ `unchecked`（列表摘要态，未核对）/ `pending`（签发失败，附 `identity_message`）。
- ⚠️ **重启动换身份**：会话跑过一次后再 start，若拓扑定义发生了变化（节点/链路/服务增删改），平台视为新的一次执行——**旧 drill_id 关闭（superseded），换发新 drill_id**。按 drill_id 归档监测/审计数据的调用方要注意这一点。

### 1.5 docker 节点运行时命名

docker 型节点启动后，容器名/节点名统一改为 `chb-<deployment_id后12位>-<节点id>`（如 `chb-263eb0496215-1`），避免与手工容器冲突。用户声明的名字保留在节点的 `display_name` 字段（GET 会话详情可见）。netns 节点不加前缀。

### 1.6 其他

- CORE 会话号（`session_id`）删除后可复用；drill_id 永不复用。
- 链路未显式配 IP 时自动按 `10.0.0.0/24` 顺序编址。
- 所有时间戳字段为 ISO 8601 字符串。

## 2. 拓扑生成

单端点：`POST /api/topology`。**一步创建 CORE 会话并搭好全部节点/链路**（不启动）。支持 JSON 与 XML 两种形态，按 `Content-Type` 自动识别。

### 2.1 JSON 形态（Content-Type: application/json）

顶层结构（TopologyInput）：

| 字段 | 类型 | 必填 | 默认 | 说明 |
|:--|:--|:--:|:--|:--|
| `schema_version` | int | 否 | 2 | 拓扑描述版本，固定填 2 即可 |
| `name` | string | 否 | "topology" | 拓扑名 |
| `options` | object | 否 | null | 会话级配置（string→string 键值对，如 emane 参数），设置后会以定义态启动一次会话 |
| `nodes` | array | 否 | [] | 网络节点定义，见 2.1.1 |
| `links` | array | 否 | [] | 链路定义，见 2.1.2 |
| `wlans` | array | 否 | [] | WLAN 无线节点定义，见 2.1.3 |
| `network_activity` | object | 否 | null | 背景流量与 IDS 探针计划（§2.1.7），随拓扑保存、随会话启动自动运行 |

#### 2.1.7 可选：network_activity 背景流量计划（2026-11-19 增补）

```json
"network_activity": {
  "traffic": [ { "id": "bg-1", "name": "后台浏览", "protocol": "http",
                 "source_id": 1, "target_id": 2, "target_link": [1, 2],
                 "port": 80, "path": "/", "rate": 5, "delay": 25, "duration": 120 } ],
  "probes":  [ { "id": "ids-1", "name": "链路IDS", "node_id": 1, "link": [1, 2], "ruleset": "verification" } ]
}
```

**traffic 字段**（≤8 条；protocol = `http`｜`tcp`｜`udp`）：

| 字段 | 约束 | 说明 |
|:--|:--|:--|
| `id` / `name` | 1-48 位 `[a-zA-Z0-9_-]` / ≤80 字符 | 任务标识与显示名 |
| `source_id` / `target_id` | int | **源必须 CORE 原生节点**；目标为任意有 IP 的业务节点（http 可打 docker；iperf3 的 tcp/udp **目标必须原生**） |
| `target_link` | `[id1, id2]` | 目标节点所连链路（用于解析接口地址） |
| `port` | 1-65535 | 目标端口（iperf 同节点端口须互异） |
| `path` | http 专用 | 必须站内路径（`/` 开头，禁 `//`） |
| `rate` | 1-10,000,000 | http 单位 = 请求/秒（**≤50**）；iperf 单位 = bps |
| `delay` | 0-3600 秒 | 启动延迟——**docker 冷启动目标强烈建议 ≥25**（就绪判定为 socket 连通，见下方实测注记） |
| `duration` | 1-3600 秒 | 运行时长，到点自动 completed |

**probe 字段**（≤4 条）：`{id, name, node_id(原生), link, ruleset}`——在原生节点接口上以被动 pcap 跑 Snort 3；`ruleset` 来自 `GET /network-activity/capabilities`（内置 `verification` 无害验收规则，特征串 `BRIDGE_IDS_CHECK`）。

**运行时查询**（随部署维度）：

| 端点 | 说明 |
|:--|:--|
| `GET /network-activity/capabilities` | 能力自检 `{http, iperf3, snort, rulesets[]}`——依赖 `/opt/core-network-tools` 工具（iperf3 需 ≥3.17 支持 `--json-stream`；Snort 3.x + LibDAQ；未安装时如实 false） |
| `GET /deployments/{deployment_id}/network-activity` | 运行批次 `{runs:[{items:{...metrics}, ...}], alerts[], startup_error}`；traffic metrics 含 `requests/successes/errors/bytes/requests_per_second`，probe metrics 含 `packets/drops/alerts` |
| `POST /deployments/{deployment_id}/network-activity/{run_id}/{item_id}/stop` | 停止单个任务项 |

**行为**：计划随会话 `start` 自动运行（start 响应带 `network_activity: {run_id, failed_items[]}`，启动前做工具 preflight）；会话 `stop/delete` 自动停止全部任务；单项失败不隔离影响其他项（探针缺工具 → 该项 failed 带明确原因）。

**实测注记**：就绪判定为 socket 连通（非真实 HTTP 探测），docker 冷启动目标在无 delay 时首批评测可能超时/出错——用 `delay` 缓解；稳态偶发 error 属 1s 超时底噪，看 `successes` 即可。

#### 2.1.1 nodes[] 节点字段（16 个）

| 字段 | 类型 | 必填 | 默认 | 说明 |
|:--|:--|:--:|:--|:--|
| `id` | int | **是** | — | 节点号，会话内唯一（与 wlans 的 id 共同去重，重复报 400） |
| `name` | string | **是** | — | 节点名；docker 型节点运行时会被改名为 `chb-...`（原名存 display_name） |
| `type` | string | 否 | "default" | 节点类型，**15 种取值**见下表 |
| `model` | string | 否 | "PC" | netns 节点型号：`router` / `host` / `PC` / `mdr`（影响 CORE 默认服务组） |
| `x`, `y` | float | 否 | 200 | 画布坐标（不影响仿真，仅展示） |
| `services` | array | 否 | null | 服务名列表；**注意**：model 有默认服务组时（router/host/PC/mdr），显式给 services 会**整体覆盖**默认组而非追加 |
| `icon` | string | 否 | null | 图标路径（仅展示） |
| `image` | string | 否 | null | docker 镜像引用；**与 instance 绑定互斥使用**（详见下方校验规则） |
| `image_ref` | string | 否 | null | 镜像引用（name:tag 形态，instance 绑定时由服务端回填） |
| `instance` | string | 否 | null | **绑定节点模板名**（实例库 /instances 中已定义的模板）；绑定后 image/services/类型由模板版本决定 |
| `instance_version` | int | 否 | null | 模板版本号；不传则解析为该模板当前最新版本 |
| `target_name` | string | 否 | null | 绑定靶标名（instance 解析后回填，调用方一般不传） |
| `target_version` | int | 否 | null | 绑定靶标版本（同上） |
| `emane` | string | 否 | null | EMANE 模型名（type=emane 时使用） |

**type 15 种取值**：

| type 字符串 | CORE NodeType | 说明 |
|:--|:--:|:--|
| `default` / `router` / `host` / `PC` | 0 | netns 虚拟节点（共享宿主 rootfs）；四者是同型的别名，行为差异由 model 决定 |
| `switch` | 4 | 交换机 |
| `hub` | 5 | 集线器 |
| `wlan` / `wireless_lan` | 6 | WLAN 无线网络（建议放 wlans[] 以携带配置） |
| `rj45` | 7 | RJ45 物理接口桥接 |
| `tunnel` | 8 | 隧道 |
| `emane` | 10 | EMANE 无线仿真 |
| `tap_bridge` | 11 | TAP 桥接 |
| `docker` | 15 | docker 容器节点（需 instance 或 image） |
| `wireless` | 17 | 无线节点（新式） |
| `podman` | 18 | podman 容器节点 |

#### 2.1.2 links[] 链路字段

| 字段 | 类型 | 必填 | 默认 | 说明 |
|:--|:--|:--:|:--|:--|
| `node1_id` / `node2_id` | int | **是** | — | 两端节点号（必须已存在于 nodes/wlans，且不能相同，否则 400） |
| `iface1` / `iface2` | object | 否 | null | 完整接口对象 `{id, name, mac, ip4, ip4_mask, ip6, ip6_mask, mtu, node_id}`（9 字段全可选）。**不传时自动分配接口号与 IP** |
| `iface1_ip4` / `iface2_ip4` | string | 否 | 自动 | **扁平写法**：直接给 IP（如 "10.0.0.1"） |
| `iface1_ip4_mask` / `iface2_ip4_mask` | int | 否 | 24 | 扁平写法的掩码 |
| `options` | object | 否 | null | 完整 QoS 对象，11 字段：`jitter, key, mburst, mer, loss, bandwidth, burst, delay, dup, unidirectional, buffer`（全可选） |
| `bandwidth` / `delay` / `loss` / `jitter` / `dup` | — | 否 | — | **扁平写法**的 QoS（任一非空即生效）；与 `options` 同时给时 `options` 优先 |

**IP 编址规则**：两端都没给 IP → 按 `10.0.0.0/24` 自动顺序分配；给了一端 → 只配该端。两种写法等效，扁平写法更简洁，推荐外部调用使用。

#### 2.1.3 wlans[] WLAN 节点字段（6 个）

| 字段 | 类型 | 必填 | 默认 | 说明 |
|:--|:--|:--:|:--|:--|
| `id` | int | **是** | — | 与 nodes 的 id 共同去重 |
| `name` | string | **是** | — | 节点名 |
| `x`, `y` | float | 否 | 200 | 坐标 |
| `range` | string | 否 | "275" | 无线覆盖范围（像素） |
| `bandwidth` | string | 否 | "54000000" | 带宽 bps |
| `delay` | string | 否 | "5000" | 延迟 μs |
| `jitter` / `error` | string | 否 | "0" | 抖动/误码 |

> 注意：wlans 的数值字段是 **string** 类型（CORE 配置项原样传递）。

#### 2.1.4 服务端校验规则（违反即 400）

| # | 规则 | 错误响应（实测） |
|:--:|:--|:--|
| 1 | 节点/ wlan ID 重复 | `{"error":"节点 ID 重复"}` |
| 2 | type 不在 15 种取值内 | `{"error":"未知节点类型: foo"}` |
| 3 | 链路端点不存在或两端相同 | `{"error":"链路端点不存在或相同"}` |
| 4 | instance 绑定时 image 与模板版本不一致 | `{"error":"节点镜像与模板版本不一致: <id>"}` |
| 5 | instance 绑定时 services 与模板版本不一致 | `{"error":"节点服务与模板版本不一致: <id>"}` |
| 6 | docker 镜像在本机不存在（inspect 失败） | `{"error":"固定的镜像已不在本机，请重新导入: <image>"}` |
| 7 | instance 解析的服务未在 daemon 注册 | `{"error":"daemon 服务未注册: <服务名>"}` |

#### 2.1.5 成功响应

```json
// 201 Created
{"session_id": 2, "deployment_id": "deploy-bc15263b10c7481288600c7c9e5d41d1", "name": "demo", "nodes": 2, "links": 1}
```

- `session_id`：CORE 会话号，**后续所有操作的句柄**
- `deployment_id`：平台部署记录号（docker 节点运行时命名前缀来源）
- **只创建不启动**，state=1（DEFINITION）；要跑起来必须再调 `POST /api/sessions/{sid}/start`

#### 2.1.6 示例

**示例 1：netns 双节点 + 显式 IP**（见 §0 快速上手，实测通过）

**示例 2：docker 实例绑定 + 交换机**（实测通过）

```bash
curl -s -X POST $B/api/topology -H 'Content-Type: application/json' -d '{
  "name": "inst-demo",
  "nodes": [
    {"id": 1, "name": "atk", "type": "docker", "instance": "drill-attacker", "x": 100, "y": 100},

# docker 节点自动: model="target", image=镜像digest, name=chb-<deploy12>-1, display_name="atk"
```

**示例 3：不用节点模板的 docker 拓扑**（image + services 直接声明，无 `instance` 字段；本例即当前环境中会话 1 的同款结构，实测部署结果与之一致）

```bash
curl -s -X POST $B/api/topology -H 'Content-Type: application/json' -d '{
  "name": "drill-ssh-chain",
  "nodes": [
    {"id": 1, "name": "attacker",   "type": "docker", "image": "target-attacker-kali:v1", "services": ["DefaultRoute"],                          "x": 100, "y": 100},
    {"id": 2, "name": "fw1",        "type": "docker", "image": "target-fw:v1",            "services": ["svc-forward"],                           "x": 250, "y": 100},
    {"id": 3, "name": "dmz-host",   "type": "docker", "image": "target-dmz-base:v3",      "services": ["DefaultRoute", "svc-httpd-41773-vuln"],  "x": 400, "y": 100},
    {"id": 4, "name": "inner-host", "type": "docker", "image": "target-inn-base:v3",      "services": ["svc-redis-unauth-vuln", "DefaultRoute"], "x": 550, "y": 100}
  ],
  "links": [
    {"node1_id": 1, "node2_id": 2, "iface1_ip4": "10.0.0.10", "iface1_ip4_mask": 24, "iface2_ip4": "10.0.0.1",  "iface2_ip4_mask": 24},
    {"node1_id": 2, "node2_id": 3, "iface1_ip4": "10.0.2.1",  "iface1_ip4_mask": 24, "iface2_ip4": "10.0.2.20", "iface2_ip4_mask": 24},
    {"node1_id": 3, "node2_id": 4, "iface1_ip4": "10.0.1.1",  "iface1_ip4_mask": 24, "iface2_ip4": "10.0.1.20", "iface2_ip4_mask": 24}
  ]
}'
# → 201 {"session_id":2,"deployment_id":"deploy-f9a17c426318406691fe2c216a24367f","name":"drill-ssh-chain","nodes":4,"links":3}
```

不使用模板的要点：
- `services` 必须是 daemon 已注册的服务名（可用服务见 §4.2 全量池；镜像清单声明的成对服务如 `svc-httpd-41773-vuln` 直接可用）
- 镜像必须已导入本机（docker inspect 验证，缺失报 400，见 §2.1.4 规则 6）
- docker 节点部署后运行名改为 `chb-<deployment_id后12位>-<节点id>`，`display_name` 保留声明名（§1.5）
- 与模板方式（示例 2）的差异：模板方式服务/镜像由模板版本锁定并登记引用；本方式完全由调用方负责一致性

**示例 4：XML 形态**（Content-Type: application/xml，实测通过）

```xml
<topology name="xml-demo">
  <node id="1" name="r1" model="router" type="router" x="100" y="100" services="zebra,OSPFv2,IPForward"/>
  <node id="2" name="pc1" model="PC" x="300" y="100" services="DefaultRoute"/>
  <node id="3" name="w1" type="wlan" x="200" y="200" range="400"/>
  <link node1="1" node2="2" iface1_ip4="10.0.0.1" iface1_ip4_mask="24" iface2_ip4="10.0.0.2" iface2_ip4_mask="24"/>
</topology>
```

XML 属性与 JSON 字段一一对应；`services` 为逗号分隔字符串；`type="wlan"` 的节点自动进 wlans 处理（携带 range/bandwidth/delay）。

**示例 5：原生 CORE XML**——根节点为 `<scenario>` 的 CORE 原生格式文件，整段 body 直接提交即可（`Content-Type: application/xml`），平台走原生导入通道（保留完整语义）：

```bash
curl -s -X POST $B/api/topology -H 'Content-Type: application/xml' --data-binary @core-scenario.xml
```

## 3. 会话生命周期

### 3.1 状态流转

```
POST /api/sessions 或 POST /api/topology
        │
        ▼
  ┌─────────────┐  POST .../start {definition:false}   ┌──────────────┐
  │ 1 DEFINITION │ ──────────────────────────────────▶ │  4 RUNTIME   │
  │  (拓扑定义)   │ ◀────────────────────────────────── │  (运行中)     │
  └─────────────┘          POST .../stop                └──────────────┘
        │                  （stop 后拓扑定义保留，可再次 start）      │
        │                                                     │ start 后再启动
        ▼                                                     ▼ 且拓扑有变更 → 新 drill_id
    DELETE /api/sessions/{sid} （任何状态可删；RUNTIME 先自动 stop 再删）
```

### 3.2 端点明细

#### 3.2.1 `GET /api/sessions` — 会话列表

#   {"id":2,"state":1,"nodes":2,"file":"","dir":"/tmp/pycore.2","identity_status":"unchecked"}
# ]
```

| 字段 | 说明 |
|:--|:--|
| `id` | CORE 会话号 |
| `state` | 状态枚举（§1.3） |
| `nodes` | ⚠️ **节点数量（int）**——列表是摘要；完整节点数组只在详情接口返回 |
| `file` | 关联的场景文件路径（原生 XML 导入时有值） |
| `dir` | 会话工作目录 |
| `identity_status` | 演练身份核对状态（§1.4） |

#### 3.2.2 `POST /api/sessions` — 创建空会话

```

#### 3.2.5 `POST /api/sessions/{session_id}/start` — 启动

```bash
curl -s -X POST $B/api/sessions/2/start -H 'Content-Type: application/json' -d '{"definition": false}'
# → {"result": true, "exceptions": []}
```

| 参数 | 位置 | 必填 | 默认 | 说明 |
|:--|:--|:--:|:--:|:--|
| `definition` | body | 否 | false | **false** = 实例化全部节点并启动声明服务（进入 RUNTIME）；**true** = 仅以定义态启动（不建运行时资源） |

> 响应增补（2026-11-19）：拓扑含 `network_activity` 计划时，`definition=false` 的成功响应额外携带 `"network_activity": {"run_id": "...", "failed_items": []}`——启动前已做工具 preflight，preflight 失败的任务列入 failed_items（带原因），不影响其余任务与其他节点启动。会话 stop/delete 自动停止全部任务。

行为要点：
- `definition=false` 时平台先冻结本次执行快照；**若拓扑定义相对上次执行有变更，旧 drill_id 关闭（superseded）并换发新 drill_id**（§1.4）
- docker 节点此时才真正创建容器，命名 `chb-<deploy12>-<节点id>`（§1.5）
- `exceptions` 数组非空表示个别节点/服务启动异常（会话整体仍可能成功）；`result=false` 表示启动失败

#### 3.2.6 `POST /api/sessions/{session_id}/stop` — 停止

```bash
curl -s -X POST $B/api/sessions/2/stop
# → {"result": true}
```

- 停止并销毁运行时资源（节点进程/容器），**拓扑定义保留**（节点/链路不丢失）
- 状态回到 1（DEFINITION），可再次 start（实测验证：stop 后 `state:1 nodes:2 links:1`）
- `result=false` 时附 `exceptions`

#### 3.2.7 `DELETE /api/sessions/{session_id}` — 删除

```bash
curl -s -X DELETE $B/api/sessions/2
# → {"result": true}     失败时 → {"result": false}
```

- 任何状态可删；**RUNTIME/DATACOLLECT 时服务端自动先补 stop 并等待退出（最多 10s）**再删
- 级联释放：实例引用锁定解除、drill_id 关闭（status=closed）、事件订阅注销
- 该会话的历史 metrics/events 保留供复盘；audit 永久保留
- 这是**唯一**清理节点进程/容器的途径——删除后 CORE 会话号可被新会话复用

#### 3.2.8 `GET /health` — 健康检查

```bash
curl -s $B/health    # → {"status":"ok","sessions":1}    bridge 或 daemon 异常时 → 503
```

## 4. 可用节点（netns / docker）及其服务

### 4.1 两型节点对比

| 维度 | netns 型 | docker 型 |
|:--|:--|:--|
| CORE NodeType | 0（DEFAULT） | 15（DOCKER） |
| topology `type` | `default`/`router`/`host`/`PC` | `docker` |
| 文件系统 | 共享宿主 rootfs | 独立镜像 |
| `model` 取值 | `router` / `host` / `PC` / `mdr`（4 种） | 固定 `target`（服务端设置） |
| `image` | **禁止**（共享宿主，不绑镜像） | **必填**（instance 绑定时由模板决定） |
| 可用服务来源 | CORE 内置 system 服务（27 个） | 绑定镜像清单（manifest）声明的演练服务 |
| 运行时命名 | 声明名即节点名 | `chb-<deploy12>-<节点id>` |
| 生命周期 | 随会话 start/stop | 容器随会话 start 创建 / stop 销毁 |

**netns 各型号的 CORE 默认服务组**（services 为空时自动附带；显式给 services 则整体覆盖）：

| model | 默认服务组 |
|:--|:--|
| `router` | zebra, OSPFv2, OSPFv3, IPForward |
| `host` | DefaultRoute, SSH |
| `PC` | DefaultRoute |
| `mdr` | zebra, OSPFv3MDR, IPForward |

### 4.2 `GET /instances/available-services` — 可声明服务总表

```bash
curl -s $B/instances/available-services
```

```json
{"ok": true, "data": {
  "drill": [
    {"name": "svc-httpd-41773-normal", "mode": "normal", "software": "httpd"},
    {"name": "svc-httpd-41773-vuln",   "mode": "vuln",   "software": "httpd"},

```

- `drill`：演练服务对（custom_services 注册，normal/vuln 成对，来自各镜像清单声明）——docker 专用
- `system`：CORE 内置基础服务（当前 27 个，实测清单）——netns 专用
- ⚠️ 同软件的 normal/vuln **互斥**（同节点只能选一个模式）；跨软件可组合
- ⚠️ 此端点是**全量池**（所有镜像清单声明的并集），**不带镜像维度**。要查"某个镜像能声明哪些服务"用下面的按镜像查询

#### 按镜像查询可用服务：`POST /targets/image/detail`

```bash
curl -s -X POST $B/targets/image/detail -H 'Content-Type: application/json' \
     -d '{"ref": "target-dmz-base:v3"}'
# → data.service_pairs 为该镜像清单声明的服务（实测）:
#   [{"name":"svc-httpd-41773-normal","mode":"normal","impl":{"startup":["bash httpd-41773-normal.sh"],"validate":["pidof httpd"],...},"owner":"drill"},
#    {"name":"svc-httpd-41773-vuln","mode":"vuln",...,"owner":"drill"},
#    {"name":"DefaultRoute","mode":null,...,"owner":"CORE 内置"}]
```

| body 字段 | 必填 | 说明 |
|:--|:--:|:--|
| `ref` | **是** | 镜像引用（name:tag） |
| `target_name` / `target_version` | 否 | 指定靶标版本取其清单（不传取最新已发布版本） |

返回关键字段：`service_pairs`（服务名/模式/实现 startup+validate/owner）、`pieces`（三件完整性 image/services/manifest/complete）、`manifest`（完整清单）、`inspect`（docker inspect 摘要）、`selected_target`（命中的靶标版本）。

**漏洞标注（2026-11-24 新增，声明性元数据）**：`service_pairs[].cve`（CVE 编号数组，如 `["CVE-2021-41773"]`）与 `service_pairs[].vulnerable`（`true` 有漏洞 / `false` 无 / `null` 未标注）——镜像包构建时在 manifest 声明，随条目带出。⚠️ 这是**纯声明元数据**：平台不验证镜像是否实际存在该漏洞，不参与就绪检查/预检；外部系统可据此选择 exploit 与靶标（如 `exploit_id=shellshock_cgi` ↔ `CVE-2014-6271`）。未声明的包此两键为 `null`/缺失。

**三层服务区分语义**：① 本端点按镜像列出可声明服务；② `POST /instances` 声明时校验池只取该镜像清单内条目，清单外报 400 `SERVICE_NOT_IN_MANIFEST`（错配在声明时拦截）；③ `available-services` 是全量枚举。同软件 normal/vuln 互斥在 ② 层校验。

### 4.3 节点模板（实例）CRUD

#### `GET /instances` — 模板列表

```json
{"ok": true, "data": [
  {
    "name": "dmz-httpd", "runtime_type": "docker", "image_tag": "target-dmz-base:v3",
    "services": [{"name": "svc-httpd-41773-vuln", "mode": "vuln"}, {"name": "DefaultRoute"}],
    "ports": [80], "cve": ["CVE-2021-41773"], "notes": "DMZ 靶标",
    "locked": false, "delete_locked": false, "referenced_by": []
  },
  {
    "name": "fw-router", "runtime_type": "netns",
    "services": [{"name": "SSH"}, {"name": "DefaultRoute"}, {"name": "NAT"}],
    "locked": false, "delete_locked": false, "referenced_by": []
  }
]}
```

- `locked`：被活跃演练引用（部署自动登记）→ 修改/删除被拒 409
- `referenced_by`：引用方列表（drill_id＋会话号 / 拓扑引用）
- `migration_error`：旧格式记录迁移告警（不影响读取，修复后消失）

#### `POST /instances` — 创建模板

| 字段 | 必填 | 说明 |
|:--|:--:|:--|
| `name` | **是** | 模板名（引用锚点，不可含路径分隔符） |
| `runtime_type` | **是** | `docker` / `netns`（仅此两值） |
| `image_tag` | docker 时**必填** | 镜像引用（name:tag）；netns 时**禁止**传 |
| `services` | 条件必填 | `[{name, mode}]` 数组；netns 且 model 属于 PC/host/router/mdr 时不许为空（CORE 会回填默认组，要求显式声明） |
| `model` | 否 | netns 型号 |
| `ports` / `cve` / `flags` / `notes` | 否 | 自由扩展元数据 |

校验规则（错误码 → HTTP）：

| code | HTTP | 触发条件 |
|:--|:--:|:--|
| `NO_NAME` | 400 | 缺 name |
| `NAME_INVALID` | 400 | 名含 `/` `\` |
| `RUNTIME_INVALID` | 400 | runtime_type 非 docker/netns |
| `IMAGE_REQUIRED` | 400 | docker 未绑 image_tag |
| `NETNS_NO_IMAGE` | 400 | netns 传了 image |
| `CORE_DEFAULT_SERVICES` | 400 | netns 未选任何服务且型号有默认组 |
| `MANIFEST_REQUIRED` | 400 | docker 绑定的镜像未编目清单 |
| `SERVICE_UNKNOWN` | 400 | 服务不在可用总表 |
| `SERVICE_NOT_IN_MANIFEST` | 400 | docker 声明了镜像清单外的演练服务 |
| `NETNS_DRILL_DENIED` | 400 | netns 声明了演练服务（演练服务为容器专属） |
| `MODE_INVALID` | 400 | 服务模式与清单不一致 / 系统服务给了 mode |
| `SERVICE_DUPLICATE` | 400 | 重复声明同一服务 |
| `SERVICES_MUTEX` | 409 | 同软件 normal/vuln 同时声明 |
| `INSTANCE_DUPLICATE` | 409 | 模板名已存在 |

#### `POST /instances/{name}` — 更新模板

- body 同创建 + `base_version`（可选乐观锁：与当前版本不一致 → 409 `VERSION_CONFLICT`）
- 模板是"模板式"语义：**修改对引用它的拓扑在下次部署时生效**，不影响已运行会话

#### `POST /instances/{name}/clone` — 复制模板（被锁定时的出路）

- body 可选 `{"name": "新名"}`；不传自动 `原名-copy` / `-copy2` …
- 复制件不受原模板引用锁定影响

#### `DELETE /instances/{name}` — 删除模板

- 被引用锁定 → 409 `INSTANCE_LOCKED` + `referenced_by`；出路①删除对应会话（自动解除）②clone 后改副本

### 4.5 原生（netns）服务池与渲染预览（2026-11-19 增补）

netns 节点的可用服务来自 CORE daemon 注册表（内置 27 个 + custom_services 自定义类），**宿主装了软件不会自动成为服务**——服务 = 声明了启动/校验方式的服务定义。

| 端点 | 说明 |
|:--|:--|
| `GET /native-services` | 服务池：`[{name, group, origin: builtin\|custom, dependencies[]}]`（`svc-`/`imgsvc-`/`imgmode-` 前缀与镜像清单占用名被排除——演练服务为容器专属） |
| `GET /native-services/{name}/defaults` | 服务默认配置（供节点级覆盖） |
| `POST /native-services/{name}/preview` | **渲染预览**：不建会话即可看服务文件在该节点上的最终渲染结果。body `{node_id, model, links[], peer_types{}, config{}}`，返回 `{files: {文件名: 渲染内容}}` |

预览示例（DefaultRoute 的 `data()` 动态钩子随预览链路计算网关）：

```bash
curl -s -X POST $B/native-services/DefaultRoute/preview -H 'Content-Type: application/json' -d '{
  "node_id": 1, "model": "host",
  "links": [{"node1_id": 1, "node2_id": 2, "iface1_ip4": "10.30.0.1", "iface1_ip4_mask": 24,
             "iface2_ip4": "10.30.0.2", "iface2_ip4_mask": 24}],
  "peer_types": {"2": "switch"}
}'
# → files["defaultroute.sh"] = "…\nip route add default via 10.30.0.1"
```

> 平台化创建/编辑/删除原生服务定义（无需手编 .py 与重启 daemon）已有设计稿（《原生服务定义平台化设计.md》），实施后本文档再行增补。

## 5. 错误码总表

### 5.1 桥接风格（`/api/*`）

错误体 `{"error", "detail", "hint"}`（detail/hint 可缺省）：

| HTTP | error | 触发 |
|:--:|:--|:--|
| 400 | invalid JSON / invalid XML | 请求体解析失败 |
| 400 | invalid alert level / invalid service action / invalid mobility action | 枚举值非法 |
| 400 | must provide position or geo | move 缺参数 |
| 400 | （中文校验文案） | 拓扑校验规则 1~7（§2.1.4） |
| 404 | session N not found | 会话不存在（gRPC NOT_FOUND 映射） |
| 404 | node N not found | 节点不存在 |
| 409 | 会话运行中不可改接口 IP | CORE 协议限制（PATCH links） |
| 415 | unsupported media type | Content-Type 不支持 |
| 500 | internal server error | 服务端异常（detail 含原因） |
| 503 | bridge unavailable / bridge not initialized | daemon 未启动或 bridge 未就绪 |

gRPC 状态 → HTTP 映射：`NOT_FOUND→404`、`INVALID_ARGUMENT→400`、`ALREADY_EXISTS→409`、`PERMISSION_DENIED→403`、`UNAVAILABLE→503`、`INTERNAL→500`，其余→500。

### 5.2 平台风格（`/instances*` `/targets*` 等）

错误体 `{"ok":false,"error":{"code","message",...}}`，code 汇总：

| 分组 | code |
|:--|:--|
| 实例/模板 | `NO_NAME` `NAME_INVALID` `RUNTIME_INVALID` `IMAGE_REQUIRED` `NETNS_NO_IMAGE` `CORE_DEFAULT_SERVICES` `SERVICE_UNKNOWN` `SERVICE_NOT_IN_MANIFEST` `NETNS_DRILL_DENIED` `MODE_INVALID` `SERVICE_INVALID` `SERVICE_DUPLICATE` `SERVICES_MUTEX`(409) `INSTANCE_DUPLICATE`(409) `INSTANCE_LOCKED`(409) `VERSION_CONFLICT`(409) `TARGET_INVALID` `MANIFEST_REQUIRED` |
| 镜像导入 | `IMAGE_REQUIRED` `IMAGE_CONFLICT`(409) `INSPECT_FAILED` `LOAD_FAILED` `EXTRACT_FAILED` `EXTRACT_UNSAFE` `BAD_PATH` `BAD_NAME` `NAME_CONFLICT` `NO_IMAGE` `NO_REF` `FILE_NOT_FOUND` `TOO_LARGE` `UPLOAD_FAILED` `RMI_FAILED` |
| 容器 | `NOT_STANDALONE`(403) `NOT_RUNNING` `NO_CMD` `RUN_FAILED` |
| 通用 | `NOT_FOUND`(404) `SESSION_NOT_FOUND` `BRIDGE_UNAVAILABLE` |

### A. 会话内节点/链路 CRUD（动态组装用）

| 端点 | 说明 |
|:--|:--|
| `POST /api/sessions/{sid}/nodes` | 加节点。body 为 NodeModel（id/name/type/model/position/services/image/instance…）；传 `instance` 时自动绑定模板并登记引用。→ `{"node_id": N}` |
| `GET /api/sessions/{sid}/nodes/{nid}` | 节点详情（含接口与链路） |
| `PATCH /api/sessions/{sid}/nodes/{nid}?icon=` | 改图标 |
| `DELETE /api/sessions/{sid}/nodes/{nid}` | 删节点（级联删其全部链路 + 解除实例引用） |
| `POST /api/sessions/{sid}/nodes/{nid}/move` | 移动节点（position 或 geo 二选一） |
| `POST /api/sessions/{sid}/nodes/{nid}/command` | 节点内执行命令 `{command, wait=true, shell=false}` → `{return_code, output}` |
| `GET /api/sessions/{sid}/nodes/{nid}/terminal` | 获取 vcmd 终端命令串 |
| `POST /api/sessions/{sid}/links` | 加链路 `{node1_id, node2_id, iface1?, iface2?, options?}`；iface 省略时自动分配空闲接口号 → `{result, iface1, iface2}` |
| `PATCH /api/sessions/{sid}/links` | 改链路（QoS 任何状态可改；接口 IP 仅定义态可改，运行中 409） |
| `DELETE /api/sessions/{sid}/links` | 删链路（需带两端 iface 完整定义） |

动态组装最小示例（实测通过）：

```bash
curl -s -X POST $B/api/sessions/2/nodes -H 'Content-Type: application/json' \
     -d '{"name": "pc2", "model": "host", "type": 0, "position": {"x": 400, "y": 100}, "services": ["DefaultRoute"]}'
# → {"node_id": 4}
curl -s -X POST $B/api/sessions/2/links -H 'Content-Type: application/json' -d '{"node1_id": 2, "node2_id": 4}'
# → {"result":true,"iface1":{"id":1,...},"iface2":{"id":0,...}}
```
