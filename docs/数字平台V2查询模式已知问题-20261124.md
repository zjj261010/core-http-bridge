# 数字平台 V2.0 查询模式已知问题

2026 年 11 月 24 日在 Bridge 提交 `53b0edc` 上验证。11 项定向测试通过。隔离 Docker 拓扑中，IF-01 无令牌受理、Q1 状态查询、Q2 读取 HTTP 200 结果、Q3 分页读取真实 Snort 告警均已跑通。停止会话后仍可查询已完成任务。额外验证发现以下三项问题，状态均为待处理。 [V2.0 设计](design/数字平台与容器平台交互设计V2.0-查询模式.md)

## 1. 任务执行中已有告警时，Q2 和 Q3 返回 500

**复现**。在隔离数据库中创建一个 `executing` 任务，记录观测开始时间，并在所属探针批次入库一条告警。任务尚未写入 `observation_end`。此时 Q1 返回 HTTP 200 和 `executing`，Q2 与 Q3 均返回 HTTP 500，日志出现 `KeyError: 'observation_end'`。

Q2 为计算告警总数读取告警，Q3 为分页读取告警。两条路径共用的 `_alerts()` 直接访问观测结束时间，而该字段在执行结束时写入。存在符合批次条件的告警时，执行中的查询会触发异常。 [观测结束时间](../validation_sequences.py#L361) · [告警读取](../validation_sequences.py#L398-L409) · [查询接口](../validation_sequences.py#L607-L641)

**验收条件**。任务处于 `accepted` 或 `executing` 时，有告警和零告警均可按接口契约查询。Q2 返回当前已完成步骤，保留未完成的任务状态。Q3 明确区分临时查询和已封存窗口的尾页。任务完成后，查询可读取完整结果。

## 2. 已完成任务的告警查询随迟到入库而变化

**复现**。封存时，任务窗口内已有一条告警。首次 Q3 查询返回一条。任务进入 `finished` 后，再写入一条抓包时间仍落在原观测窗口内的告警。同参数再次查询，结果从一条变为两条。封存的旧 IF-03 报文仍只有一条。

Q3 每次从活动事件表按窗口重新计算，Q2 的 `alerts_total` 也走该路径。只冻结观测状态和结束时间仍允许之后写入的事件改变查询结果，违反 V2.0 对 `finished` 结果的冻结约定。 [封存逻辑](../validation_sequences.py#L432-L464) · [Q2 数据组装](../validation_sequences.py#L553-L581) · [Q3 查询](../validation_sequences.py#L616-L641)

**验收条件**。任务封存时固定可查询的告警集合或等效的事件边界。在约定保留期内，迟到事件入库后，使用同一查询参数仍得到相同告警、总数和分页游标。Q2 的总数与 Q3 遍历结果一致。

## 3. 查询模式仍为新任务生成旧回传记录

**复现**。不配置回调地址，执行一次完整的 `HttpServiceCheck`。任务结束后，Q1、Q2、Q3 正常读取，但运行记录中仍有 `pending` 的 IF-02 和 IF-03。随后在同一隔离环境配置模拟回调并重启 Bridge，接收端依次收到 IF-02 和 IF-03，双方确认后两条记录均为 `confirmed`。

当前封存逻辑为新任务生成旧投递记录，回调地址为空时发送线程暂缓投递。V2.0 第 4.3 节约定投递表仅保留历史数据。按当前行为长期使用查询模式会积累待发送记录，后续配置回调时还可能触发历史任务投递。 [投递记录创建](../validation_sequences.py#L427-L461) · [发送条件](../validation_sequences.py#L528-L550) · [V2.0 投递约定](design/数字平台与容器平台交互设计V2.0-查询模式.md#43-与-v11-投递设计的差异说明)

**验收条件**。按 V2.0 查询模式完成新任务后，三项查询均正常，旧投递表无该任务的新记录。已有历史投递数据仍可依照确定的兼容策略读取。若保留推送模式，应在对接文档中明确启用条件及历史队列处理方式。
