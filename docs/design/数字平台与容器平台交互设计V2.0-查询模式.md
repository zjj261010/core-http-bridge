# 数字平台与容器平台交互设计 V2.0 —— 查询模式

> 版本：V2.0 · 2026-11-24 · 容器平台侧修订
> 替代：《数字平台与容器平台交互设计 V1.0》中的 IF-02/IF-03 上传通道设计，及《开发说明书 V1.1》中的回传投递设计
> 状态：容器平台侧已实现核心（受理/执行/持久化/部署内查询），本文档为对接数字平台的正式接口契约与修订说明

---

## 一、总体设计

### 1.1 架构变更摘要（V1.0 → V2.0）

| 变更 | V1.0（原设计） | V2.0（本设计） |
|:--|:--|:--|
| 结果获取 | 容器平台**推送** IF-02（结果序列）与 IF-03（告警分批）到数字平台 | 容器平台**持久化保存**，数字平台**主动查询**（拉模式） |
| 状态感知 | 依赖 IF-02 到达隐式感知完成 | 新增**状态查询接口**：数字平台随时查询任务执行状态 |
| 回调配置 | 数字平台提供接收端地址/Token，容器平台配置回调 | **取消**：无需回调地址与回调 Token，零配置对接 |
| 可靠性责任 | 容器平台负责投递重试/幂等/断线补发 | 容器平台负责**保存**（本地持久化不丢失）；数字平台按需查询，查询即得全量 |
| IF-01 下发 | 保留，不变 | 保留，不变 |

### 1.2 变更动因

1. **单向依赖更简单**：拉模式下网络方向单一（数字平台 → 容器平台），容器平台无需知道数字平台地址、无需回调鉴权配置、无投递重试/断线补发等复杂度；
2. **保存即交付**：容器平台本就将任务/步骤/告警持久化（SQLite），查询接口只是把已存数据读出来——"留出接口"比"维护推送管道"成本更低；
3. **离线友好**：数字平台离线期间容器平台照常执行与保存；数字平台恢复后一次性查询补齐，无积压队列概念。

### 1.3 交互通道总览（V2.0）

| 编号 | 接口 | 方向 | 提供方 | 状态 |
|:--|:--|:--|:--|:--|
| IF-01 | 攻击动作序列下发 | 数字平台 → 容器平台 | 容器平台 | **保留**（已实现） |
| **Q1** | 任务状态与步骤查询 | 数字平台 → 容器平台 | 容器平台 | **新增（替代 IF-02 的感知职能）** |
| **Q2** | 执行结果序列查询 | 数字平台 → 容器平台 | 容器平台 | **新增（替代 IF-02）** |
| **Q3** | Snort 告警查询 | 数字平台 → 容器平台 | 容器平台 | **新增（替代 IF-03）** |

调用时序：数字平台推演产生攻击动作序列 → IF-01 下发 → 容器平台受理并异步执行（数字平台可随时 Q1 查询进度）→ 执行结束（或中断封存）后，数字平台 Q2 拉取整条结果序列、Q3 分页拉取告警 → 入库并触发闭环校准。一次实测任务对应一次 IF-01、任意次 Q1、至少一次 Q2、任意次 Q3（支持增量游标）。

**数据保存承诺**：容器平台对已受理任务的全部数据（任务、逐步结果、窗口内告警）**本地持久化**（SQLite），数字平台离线/查询缺失期间数据不丢失、不过期；确认入库后由数字平台决定是否申请清理（一期不做清理接口，保存 forever）。

**任务标识**：一次实测任务由 (scenario_id, sequence_id) 二元组唯一确定，所有查询接口必须携带，容器平台据此定位。

## 二、IF-01 动作序列下发（保留，V2.0 无接口变化）

契约与 V1.0 §2 完全一致（路径/报文/鉴权/错误码），此处仅列**实装差异与补充**（以容器平台 b5438da+ 代码实况为准）：

### 2.1 前置配置（容器平台侧）

| 环境变量 | 必配 | 说明 |
|:--|:--:|:--|
| `BRIDGE_VALIDATION_TOKEN` | **否（2026-11-24 鉴权关闭）** | 默认未配置 = 接口组开放、不鉴权（访问控制靠内网隔离＋端口准入，同平台整体安全模型）；配置后 IF-01 启用 Bearer 校验（可选加固，纯配置可逆） |
| `BRIDGE_VALIDATION_CALLBACK_URL` | **否（V2.0 取消）** | V1.0 用于回传；拉模式无需配置 |
| `BRIDGE_VALIDATION_CALLBACK_TOKEN` | **否（V2.0 取消）** | 同上 |

### 2.2 拓扑前置标记（部署时固化）

| 标记 | 约束 |
|:--|:--|
| 序列执行节点（`validation_source`） | 每拓扑至多一个；本机 CORE 原生/Docker 节点；全部动作由该节点发起 |
| HTTP 验证目标（`validation_http_port`） | 每拓扑至多一个；目标节点声明此端口表示有可验证 HTTP 服务 |

标记在容器平台拓扑编辑页节点属性设置，随部署固化。旧拓扑无标记仍可正常运行，但受理验证任务会报 1001/1003。

### 2.3 一期可执行动作

`HttpServiceCheck`（预置 HTTP 服务检查：从执行节点向目标 `{ip}:{port}` 发起受限 HTTP GET，2xx 即 SUCCESS）。

动作字典目录当前版本 `validation/2`：预置可执行条目 1 条（HttpServiceCheck）＋ CybORG 红方动作空间参考条目 9 条（仅供对照，**不可执行**，字典目录只读——运行期增删改已关闭，目录随容器平台代码版本发布）。动作映射表真实化（ExploitRemoteService 按 exploit_id 特化命令模板）为已立项演进项；靶标库已产出 6 组实测素材（shellshock_cgi / heartbleed_ssl / sqli_login_bypass / proftpd_modcopy / phpmailer_10033 / es_groovy_1427，含命令模板与成功判据，见 action-dictionary-drafts.json）。

### 2.4 实测错误码（IF-01）

| code | HTTP | 触发条件 | 说明 |
|:--|:--:|:--|:--|
| 0 | 200 | 受理成功 | — |
| 1000 | 401 | Bearer Token 缺失/错误（**仅配置了 `BRIDGE_VALIDATION_TOKEN` 时才可能返回；默认鉴权关闭**） | 校验顺序：报文格式校验（1004）先于鉴权（1000，仅启用时） |
| 1001 | 409 | 会话不存在/未运行；或会话运行实例已变化（重启/复用） | scenario_id 须为**当前运行**会话 |
| 1002 | 400 | 动作名不在字典目录内 | 字典只读，按版本对齐 |
| 1003 | 409 | 源/目标节点不可达或未标记 | 未标记验证角色/端口的拓扑无法受理 |
| 1004 | 400 | 请求格式无效（字段缺失/类型错/seq 不连续/超上限 64 步） | 校验先于鉴权执行 |
| 1005 | 409 | 相同幂等键、报文内容不同 | sequence_id 复用冲突 |
| 1006 | 409 | 该会话已有未完成验证序列 | 一期每会话串行执行一个序列 |
| 1501 | 503 | CORE 会话状态暂不可确认 | CORE 不可达等瞬时问题（原"接口未启用"分支已随鉴权关闭取消） |

## 三、查询接口组（V2.0 新增，数字平台 → 容器平台）

所有查询接口为只读 GET，UTF-8 JSON，不鉴权（2026-11-24 定稿：接口组默认开放，访问控制靠内网隔离＋端口准入；IF-01 亦同，配置 `BRIDGE_VALIDATION_TOKEN` 可选启用 Bearer 校验）。

**执行中任务同样可查**：`accepted`/`executing` 态下 Q1 返回实时步骤状态，Q2 只返回**当前已完成步骤**（进行中步骤不误标终态），Q3 以开放窗口返回已入库告警；`finished` 后按 §4 冻结语义返回。**数据冻结实现**：封存时固定观测结束时间与事件上界（observation_end_id），迟到入库的告警不改变已封存任务的任何查询结果。

### 3.1 Q1 任务状态与步骤查询

```
GET /api/v1/attack-sequences/{sequence_id}?scenario_id={scenario_id}
```

**用途**：数字平台随时查询任务执行进度（受理/执行中/已结束＋逐步状态），决定何时拉取 Q2/Q3。建议轮询间隔 2–5 秒。

**响应**（任务未结束时也可查询——返回**当前已发生**的状态与步骤；任务结束时 `state=finished` 且结果冻结）：

```json
{
  "scenario_id": "41",
  "sequence_id": "demo-001",
  "state": "finished",
  "observation_status": "complete",
  "dictionary_version": "validation/2",
  "source_node_id": 2,
  "target_node_id": 1,
  "created_at": "2026-11-24T06:30:00.000Z",
  "steps": [
    { "seq": 1, "action_name": "HttpServiceCheck", "state": "SUCCESS",
      "duration_sec": 0.42, "http_status": 200, "reason": null }
  ]
}
```

| 字段 | 说明 |
|:--|:--|
| `state` | `accepted`（已受理待执行）/ `executing`（执行中）/ `finished`（已结束，结果冻结） |
| `observation_status` | 同 §3.3 Q3；任务未结束时可为 null |
| `steps[].state` | `pending` / `running` / `SUCCESS` / `FAIL` / `SKIPPED` |
| `steps[].reason` | 失败/跳过原因（`http_check_failed` / `http_check_timeout` / `node_or_interface_unavailable` / `interrupted_outcome_unknown` / 前序失败说明） |

**并发任务**：同一会话同时只有一个任务（1006 拒绝第二个），Q1 按 sequence_id 精确查询互不干扰。

### 3.2 Q2 执行结果序列查询

```
GET /api/v1/attack-sequences/{sequence_id}/results?scenario_id={scenario_id}
```

**用途**：任务 `state=finished` 后拉取整条结果序列（等价 V1.0 IF-02 的 payload.results），数字平台据此入库校准。

**响应**（结构与 V1.0 IF-02 payload 一致，数字平台入库代码可复用）：

```json
{
  "scenario_id": "41",
  "sequence_id": "demo-001",
  "dictionary_version": "validation/2",
  "state": "finished",
  "observation_status": "complete",
  "results": [
    { "seq": 1, "action_name": "HttpServiceCheck", "actual": "SUCCESS",
      "exit_code": 0, "reason": null,
      "started_at": "2026-11-24T06:30:00.000Z", "ended_at": "2026-11-24T06:30:00.420Z",
      "duration_sec": 0.42, "source_node_id": 2, "target_node_id": 1,
      "stdout_digest": "HTTP 200" }
  ]
}
```

**语义保证**：
- `finished` 后结果冻结，重复查询返回完全相同内容（数字平台可安全重复拉取）
- `results` 条数与受理步数一致，按 seq 排列
- 任务未结束即查询：返回当前已完成步骤（`state≠finished` 提示数字平台稍后再取）

### 3.3 Q3 Snort 告警查询

```
GET /api/v1/snort-alerts?scenario_id={scenario_id}&sequence_id={sequence_id}&after_event_id={event_id}&limit=100
```

**用途**：分页拉取该任务观测窗口内的 Snort 告警（等价 V1.0 IF-03 的 alerts，从推送变分页拉取）。

| 参数 | 必填 | 说明 |
|:--|:--:|:--|
| `scenario_id` / `sequence_id` | 是 | 任务定位 |
| `after_event_id` | 否 | 增量游标：只返回该 event_id 之后的事件（首次查询不传，取全部） |
| `limit` | 否 | 默认 100，上限 500 |

**响应**：

```json
{
  "scenario_id": "41",
  "sequence_id": "demo-001",
  "observation_status": "complete",
  "is_last": true,
  "total": 37,
  "alerts": [
    { "event_id": "run-xxx:815", "probe_id": "probe-1", "seq": 3,
      "ts": "2026-11-24T06:30:05.200Z", "sid": "1:1000001", "priority": 3,
      "src_ip": "10.99.0.10", "src_port": 40211, "dst_ip": "10.99.0.1", "dst_port": 8080,
      "proto": "TCP", "msg": "Bridge IDS verification" }
  ]
}
```

- `is_last=true` 表示已到窗口末尾（`after_event_id` 游标推进到最后一条返回的 event_id 即完成全量拉取）
- `alerts[].seq`：可唯一归属某步时为该步 seq，否则 null（背景流量重叠场景）
- 告警窗口与归属算法与 V1.0 §3.2 语义一致（观测窗口内＋五元组精确匹配＋时间窗唯一归属）

## 四、数据保存与生命周期（V2.0 承诺）

### 4.1 保存范围与期限

| 数据 | 保存位置 | 期限 |
|:--|:--|:--|
| 任务/受理回执/步骤结果 | 容器平台 SQLite（validation_tasks/steps） | 永久（一期不做清理；确认入库后可由双方协商清理策略，二期候选） |
| 窗口内 Snort 告警 | 容器平台 events 表（结构化） | 随 events 保留策略（90 天）——**数字平台应及时拉取入库** |
| 执行期流量/会话 | 不保存（仅窗口内告警入库） | — |

### 4.2 状态机

```
accepted ──执行──> executing ──全部步骤完成/中断封存──> finished
    │                    │
    └── (会话不可用等) ──┴──> 封存为 finished（interrupted 语义, reason 记录）
```

- `finished` 后 Q2/Q3 数据冻结不再变化；数字平台拉取后即可入库校准
- 任务不因会话停止而丢失：封存时保留已知事实（§3.1 steps.reason 可区分）

### 4.3 与 V1.1 投递设计的差异说明

V1.1 的 validation_deliveries 投递队列/退避重试/确认游标机制在**拉模式（默认）下完全不产生新数据**——2026-11-24 起封存仅在**显式配置 `BRIDGE_VALIDATION_CALLBACK_URL`（推送模式 opt-in）**时才生成本任务的 IF-02/03 投递记录并由发送线程投递；未配置回调 = 查询模式，投递表零新记录。

**历史队列兼容策略**：表内存量记录保留可读（`GET /deployments/{id}/validation-sequences` 列表与手动 retry 端点不变）；若重新配置回调地址，存量 pending/blocked 记录按既有退避策略恢复补发——需要彻底静默的部署不要配置回调变量。

## 五、闭环修正（逻辑不变，数据获取方式变更）

V1.0 第四章的闭环语义完全保留：action_records 逐步事实 → 按 (action_name, scenario_id) 聚合校准表（n / success_rate / duration_mean / alert_rate）→ 人工确认采纳 → 推演裁决取实测值＋训练环境参数同步。

**变更仅为数据获取方式**：数字平台不再被动接收 IF-02/03 推送，而是按 §3.2/§3.3 主动拉取后入库。聚合触发条件从"每次落库后触发"变为"每次拉取后触发"（或数字平台定时轮询，效果等价）。

人工确认、偏差高亮、状态 PENDING/ADOPTED/REJECTED、两个生效点等语义不变。

## 六、动作映射字典（只读目录 + 漏洞标注对齐）

字典目录由容器平台持有并**只读**（运行期增删改已关闭——IF-01 语义依赖稳定字典版本），随容器平台代码版本发布：

| 条目类型 | 条目 | 可执行 |
|:--|:--|:--|
| 预置可执行 | HttpServiceCheck（预置 HTTP 服务检查） | ✓ 一期唯一可执行动作 |
| CybORG 参考条目 ×9 | DiscoverRemoteSystems / ServiceDiscovery(激进1·隐蔽3) / DiscoverDeception / ExploitRemoteService / PrivilegeEscalate / DegradeServices / Impact / Withdraw / Sleep | ✗ 仅供对照（simulation_steps 标注） |

字典版本 `validation/2` 起步，每次目录内容变更随容器平台代码版本递增（`validation/<n>`），随 IF-01 回执与 Q2 报文钉定回传。

**动作映射真实化演进**（已立项）：ExploitRemoteService 按 `params.exploit_id` 映射到具体利用命令模板——靶标库已实测产出 6 组素材（exploit_id ↔ 命令模板 ↔ 成功判据 ↔ CVE），与镜像漏洞标注（`service_pairs[].cve`）双向对齐；真实化后 `dictionary_version` 随容器平台发布递增，本节字段规格不变。

## 七、案例（对照 V1.0 案例改写为查询模式）

场景 scn-2026-001（4 节点，目标 8080 端口 HTTP 服务＋Snort 探针已部署），序列 demo-001 共 1 步 HttpServiceCheck。

### 7.1 下发（IF-01，与 V1.0 相同）

```bash
curl -s -X POST https://bridge.example.com/api/v1/attack-sequences \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"scenario_id":"41","sequence_id":"demo-001","actions":[
        {"seq":1,"action_name":"HttpServiceCheck",
         "target_node":{"subnet":"lab","ip":"10.99.0.1"}}]}'
# → HTTP 200 {"code":0,"message":"accepted","scenario_id":"41",
#             "sequence_id":"demo-001","dictionary_version":"validation/2"}
```

### 7.2 轮询状态（Q1）

```bash
curl -s 'https://bridge.example.com/api/v1/attack-sequences/demo-001?scenario_id=41'
# → {"state":"executing","steps":[{"seq":1,"state":"running",...}]}
# → 完成后 {"state":"finished",...}
```

### 7.3 拉取结果（Q2，等价原 IF-02 数据）

```bash
curl -s 'https://bridge.example.com/api/v1/attack-sequences/demo-001/results?scenario_id=41'
# → results[0].actual=SUCCESS, stdout_digest="HTTP 200"
```

### 7.4 拉取告警（Q3，等价原 IF-03 数据，分页游标）

```bash
curl -s 'https://bridge.example.com/api/v1/snort-alerts?scenario_id=41&sequence_id=demo-001'
# → {"observation_status":"complete","is_last":true,"alerts":[...]}
```

数字平台入库并触发闭环校准——逻辑与 V1.0 §4 一致，数据获取从被动接收改为主动拉取。

## 八、与 V1.0/V1.1 的差异与迁移对照

| 项 | V1.0/V1.1（推模式） | V2.0（拉模式） | 数字平台侧改造 |
|:--|:--|:--|:--|
| 结果获取 | 实现 IF-02 接收端 | 实现 Q2 查询调用 | 新增查询客户端，删除接收端 |
| 告警获取 | 实现 IF-03 接收端（批/确认） | 实现 Q3 分页查询 | 同上 |
| 完成感知 | IF-02 到达即知 | Q1 轮询 state=finished | 新增轮询逻辑 |
| 回调配置 | 提供地址/Token | **取消** | 无 |
| 中断补发 | 容器平台重试队列 | 查询天然幂等，重查即可 | 无 |
| 接收端幂等 | 需处理重复投递 | 无重复投递概念 | 无 |

**容器平台侧已实现/已验证**：IF-01 受理（鉴权/幂等/错误码）、执行器（逐步记录/失败即停/中断封存）、数据持久化、**Q1/Q2/Q3 三个查询端点（2026-11-24 端到端实测通过——真实 Snort 探针告警链路、seq 归属、分页游标、finished 后数据冻结）**、Snort 告警结构化落库与窗口归属算法、定向测试 225 项含隔离库验收。
