## A. 已修复①：Snort 探针在容器网卡上零告警（`network_activity.py:_snort_args`）

**现象**：全 Docker 拓扑（CORE DockerNode 节点）上部署 Snort 探针，进程正常、`perf_monitor` 计数正常、规则加载正常，但**永远零告警**。

**根因**：Docker/veth 网卡存在**校验和卸载**（checksum offload），抓到的包校验和是坏的；Snort 默认「校验通过才检测」，坏校验包被静默跳过（`tcp bad_tcp4_checksum > 0` 与零告警同时出现即为佐证）。

**修复**：`_snort_args` 增加 `-k none`（关闭校验和检查）。修复后同拓扑同规则集立即出告警（ET POLICY Apache 2.4.49 等大量命中并入库）。

## B. 已修复②：规则预检分词器把 URL 中的 `#` 误判为注释（`network_activity.py:RULE_TOKEN`）

**现象**：`POST /network-activity/rulesets/import` 导入 Cisco Talos 官方 Snort3 Community Rules（4040 条）被拒：`规则声明不完整，请检查规则头和括号`。而 `snort -T` 本体对同一文件 0 warnings 通过。

**根因**：`RULE_TOKEN` 把所有位置的 `#` 都切为注释 token。Talos 规则里 103 条含 `reference:url,www.virustotal.com/#/file/...`——URL 中的裸 `#` 被当成行注释，该行剩余部分（含结尾 `)`）被跳过 → 括号平衡检查假阳性。

**修复**：`#` 仅在行首/空白后（`(?<!\S)#`）才视为注释；裸 token 中的 `#` 自然跳过。修复后 4040 条全量通过结构检查与 `snort -T` 验证、成功导入。

## C. 待上游修改：镜像服务命名前缀的三段式机制存在两个毛边

### C.0 现状：名字三段生命周期（设计如此）

| 阶段 | 名字形态 | 产生机制 | 用途 |
|:--|:--|:--|:--|
| ① 源码原名 | `osvc-frr` | 服务定义 .py 的 `name` | 仅存在于导入前 |
| ② 包前缀名 | `svc-<包名>-<原名>` | 导入落位自动改写（`target_admin._import_delivery`） | manifest 登记 / 实例声明 / ServiceManager 当前版 |
| ③ 版本别名 | `svc-<12hex>-v1-<原名>` | 版本固化自动生成（`versions.execution_mapping`） | 不可变修订：部署时 `versions.resolve` 自动把实例声明解析为别名，节点实际挂别名 |

实测各层（osvc-router 包）：落位文件类名=②、manifest v1 services=②、实例声明=②、节点运行时=③——**链路本身自洽**。旧包（drill-httpd 等）无双名是因为导入早于版本机制上线。

### C.1 毛边①：`/instances/available-services` 重复暴露当前名与版本别名

**现象**：`drill` 与 `image` 分组同时列出 `svc-osvc-router-osvc-frr`（②）和 `svc-009bf8a91f97-v1-osvc-router-osvc-frr`（③）两条，用户可见两个"同一服务"。仅影响**版本机制上线后新导入**的 manifest 型包（旧包注册名唯一）。

**位置**：`target_admin._available_services()`——`_service_registry()` 返回全部注册名（含版本别名快照目录 `version_<key>_<n>/` 里的类名），未过滤别名。

**建议修法**：按别名模式过滤（版本快照目录的产物有固定模式）：
```python
_VERSION_ALIAS = re.compile(r'^(img)?svc-[0-9a-f]{12}-(?:v|r)\d+-')
# _available_services 中: for name in sorted(_service_registry()):
#     if _VERSION_ALIAS.match(name): continue   # 版本别名不进可用列表（部署解析仍走 versions.resolve）
```

### C.2 毛边②：混入手放文件的源会被版本固化，且删除快照文件无效

**现象**：首次 bundle 导入时若 `services/` 目录混入非导入产物（本例：操作方手工预放的 `service.py`），其类会与标准落位文件**双双固化**进版本发布记录；事后删除 `custom_services/version_<key>_1/service.py` 无效——`versions.materialize` 在 daemon 重启/再次 publish 时从 `published['sources']` **重建**快照文件（实测：删除后重启 daemon，文件带新 mtime 回归，ServiceManager 重新注册出第三个名字 `svc-<key>-v1-osvc-frr`）。

**影响**：注册表出现指向同一实现的多个名字；available-services 多一项垃圾；无功能破坏但污染可见列表。

**建议修法（两选一或组合）**：
1. **materialize 增量同步而非追加**：重建快照目录前清点 `published['sources']`，删除目录内**不在当前 sources 集合**中的 `.py`（快照目录是发布记录的派生物，应与发布记录严格一致）；
2. **导入入口防混入**：`_read_bundle`/`_import_delivery` 落位前把 `services/*.py` 中与标准改名产物冲突/重复的输入去重（或 bundle 模式禁止包内 `services/service.py` 与改名产物同名并存），从源头保证发布记录 sources 干净。

**操作侧规避**（在修复合入前有效）：bundle 的 `services/` 只放标准交付件；污染发生后用「重发布新版本」消除（新版本 sources 干净则新快照干净，旧快照仅遗留可见名字）。

### 复现路径（C 全部）

```bash
# 1. 构造含一个自定义服务的 bundle 并导入（manifest 型，非 catalog）
#    services/ 同时混入一份手写 service.py（类 name=自定义原名）
curl -X POST '.../targets/import/bundle' -d '{"dir": "<包目录>"}'
# 2. 观察导入 receipt：names 出现 svc-<包名>-<原名>（改名✓），同时版本固化后
#    custom_services/version_<key>_1/ 内出现两个 .py（混入件 + 标准件）
# 3. GET /instances/available-services：drill/image 分组各出现 2 条（②与③并存）
# 4. 删除 version_<key>_1/service.py 后重启 core-daemon：文件被 materialize 重建
```
